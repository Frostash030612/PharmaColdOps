## 1. 项目概述

PharmaColdOps 面向药品冷链运输与仓储中的温度偏移评估，以确定性规则引擎产生可追溯的处置建议，并将补发需求连接到配送优化与知识图谱查询。批次处置分为放行、隔离、复检和报废四类；补发是独立物流动作，不是第五个互斥处置类别。

项目覆盖 IRS 的决策自动化、资源优化、知识发现与数据挖掘、认知系统四个技术组。交付目标是在受控的新加坡配送算例中演示“温度事件 → 处置建议 → 补发单 → 配送方案 → 证据查询”的最小闭环。风险预测与候选根因分类作为离线实验，不进入处置 API。

本项目现已具备规则引擎、双语界面、独立标注场景库、离线 ML 基线、新加坡路线求解、订单驱动的补发求解、KG 结案写入代码，以及唯一的 Vue 客户端（旧 vanilla 静态页已于 2026-09-12 退役，故 Vue 是唯一前端）。在线模式下客户端会求解并展示已结案案例的补发路线、查询该案例的图谱证据，并把该案例提交进实时配送作业——预留库存、分配车辆、发车、按模拟时钟跟踪、逐单送达。图谱链路已于 2026-09-13 在 `docker compose` 管理的 Neo4j 上完成端到端验证。结案表单传入异常地点字段、扩充候选目的地池仍待建设。本原型不替代质量负责人的最终审批，不宣称已通过生产环境或正式合规验证。

## 2. 问题定义

温度偏移发生后，质量人员需要核对产品要求、偏移条件与包装信息，记录评估理由，再协调后续供应。项目关注三个可验证的问题：

- 同一套书面规则能否被稳定实现，并暴露规则文本与人工判断之间的分歧？
- 在车辆容量与配送时间窗约束下，优化方案相对贪心基线能改善多少距离和服务可行性？
- 用户能否从结案记录追溯输入、规则路径与证据，并在缺少记录时获得明确反馈？

减少人工评估时间、避免不当处置和缓解供应中断是预期业务价值。当前没有真实运营对照试验，不能将其表述为已量化实现的收益。

## 3. 背景与领域基础

### 3.1 法规原则与适用边界

领域知识来源包括 WHO TRS 961 Annex 9、EU GDP 2013/C 343/01、ICH 稳定性与质量风险管理指南，以及 CDC/WHO 公开程序性指引。具体产品的可接受偏移窗口仍需对应产品的稳定性证据。[WHO](https://www.who.int/publications/m/item/trs961-annex9-modelguidanceforstoragetransport)、[EU GDP](https://eur-lex.europa.eu/legal-content/EN/TXT/?uri=CELEX%3A32013C0343)、[ICH](https://www.ich.org/page/quality-guidelines)

本项目区分公开领域原则、产品稳定性资料和工程假设。当前配置记录了来源与限制，但允许偏移时长、MKT 阈值、部分复检设置及规则倍率仍含工程假设，不是法规直接给出的通用数值。关联法规节点不证明某个阈值已得到产品级验证。

CDC 的疫苗偏移指引要求暂停使用受影响疫苗，并联系免疫项目或厂商获取处置指导。本原型输出应理解为待质量复核的建议，不能用演示阈值直接授权实际产品放行或销毁。[CDC 储存与处理指南](https://www.cdc.gov/pinkbook/hcp/table-of-contents/chapter-5-vaccine-storage-and-handling.html)

### 3.2 相关工作与方法选择

Solomon 的 VRPTW 基准提供带容量和时间窗的标准配送问题。本项目用 6 个实例比较算法，再用新加坡道路矩阵展示地理场景。OR-Tools Routing Solver 提供路径构造与局部搜索，本项目采用限时 Guided Local Search。[Solomon, 1987](https://doi.org/10.1287/opre.35.2.254)、[OR-Tools](https://developers.google.com/optimization/routing/routing_options)

风险实验采用逻辑回归、LightGBM 和 XGBoost；SHAP 用于解释模型对表格特征的依赖。认知模块采用结构化图谱和模板查询，范围限定为已存储案例、规则及证据。方法原始论文见 §14。特征归因和观察数据上的原因分类不等于因果识别。

项目贡献是上述方法在受控流程中的集成与可复现评估，不主张提出新基础算法或首次将这些技术用于冷链。

### 3.3 市场背景与定位

商业产品已覆盖温度监控、运输可视化和部分质量流程自动化。例如，Controlant 的 Product Stability Automation 描述了依据产品稳定性档案自动确定放行状态的能力，不能把现有厂商概括为“只告警、没有处置能力”。[Controlant 产品说明](https://www.controlant.com/applications)

本项目定位为可检查规则、可复现实验、可演示配送联动的教学研究原型。比较维度包括规则透明度、证据追溯、配送接口和部署范围；未核实的竞品能力标为未知，不把缺少公开说明视作功能不存在。市场价值仍需用户访谈和运营数据检验。

## 5. 总体系统方案

### 5.1 目标工作流

1. 输入有明确产品类别的温度事件。当前通过表单或演示数据输入，序列解析为后续数据任务。
2. 规则引擎返回四类处置之一、补发标志、规则编号、理由和证据状态。
3. 质量人员复核建议。当前结案仅保存输入与系统建议；最终人工决定与审批人字段待设计，配送运行状态另记接受、出发与逐单送达。
4. 需要补发时，依据已确认的契约提交含目的地、数量与时间窗的模拟补发单，交由单仓求解器求解。契约、求解器与运行状态持久化均已实现并通过测试；案例—订单—路线连接于 2026-09-12 落地，并在 2026-09-13 完成端到端复核。Vue 客户端经 `/api/dispatch/*` 端点完成排线、发车、模拟时钟跟踪与紧急插单；已结案案例可被提交进该实时作业（预留库存并分配车辆）。
5. 关联案例和配送结果，展示站序、距离、排程与未服务订单，并查询本次案例的图谱证据。案例—订单—路线—证据的关联与前端查询接线已于 2026-09-12 接通（离线模式保留固定演示路线与关键词问答兜底）；选择目的地与数量的界面待建。

结案归档不等于获得真实业务结果。自动反馈学习不在 MVP 内。

### 6.2 规则处置

输入为产品类别、偏移温度、持续分钟数、MKT、包装状态和运输阶段。阶段目前随记录保存，不改变规则分支；历史异常尚未作为判定特征。4 个类别原型为 vaccine_2_8、frozen_m20、insulin_2_8、mrna_ultracold，均不代表已验证的品牌产品配置。

规则按优先级匹配，首条命中即结束：冻结风险、包装破损并超温、严重时长/MKT 越限、一般时长/MKT 越限、可复检产品近限值、其余情形。输出为 release / quarantine / retest / scrap。当前在 quarantine 或 scrap 时将 reshipment_required 设为 true，这是需单独验证的物流默认策略。

行为源为 rules_config.json 和 Python 引擎，前端离线版实现相同语义。沙箱覆盖值仅作用于当前请求，并随结案保存。已知限制包括非冻敏产品低温越界与单阈值近似多级稳定性窗口；第 4 条的隔离/报废二选一已由 rubric v1.1（2026-09-14）定为 `scrap`（rubric 与引擎同批更新），但该档背后的低温条证据缺口仍未闭合，且二者均不再产出 `quarantine`。不会为了提高 gold 一致率直接修改规则或标签。

### 6.3 风险分类与候选原因分析

风险任务以 8,000 条运输级摘要中的 silent_failure 为目标，比较 LR、LightGBM、XGBoost，并对可解释特征与加入匿名特征的版本作对照。当前采用 70/15/15 分层随机划分，验证集选择 F1 阈值，填补与缩放仅在训练集拟合。特征包括运输时长、温度摘要、开门次数和湿度统计，不能直接表述为使用当前 API 的 MKT 或阶段字段。

该数据没有时间戳，也没有相对预测时刻定义的前瞻标签，因此定位为运输级失效分类，不声称提前 30/60 分钟预警。原界面风险指数与 cause_code 仍来自确定性启发式；新增 M4 面板另外展示明确的模型估计，不能把两者混写。原 LR/LGBM/XGB 表为历史离线基线，本机部署训练采用 13 个不含 ID／量货的运输摘要特征，并按验证集选型，实际算法与留出结果见 M4 集成文档。

候选原因任务在设施月度仿真数据的 16,192 条热/冻偏移记录上区分 10 类原因，当前采用 80/20 分层随机划分。特征为设备、电源、监测及疫苗上下文；需检查诊断时可用性及同设施记录跨集合的影响。结果列能否作为输入应按任务时点论证。SHAP 表示模型关联，不证明设备故障的因果关系。

### 6.4 配送优化

模型为单仓、同容量车辆、客户服务时间窗、服务时长及返仓时限约束的 VRPTW，目标是最小化行驶距离。实现使用 RoutingModel、PATH_CHEAPEST_ARC 初解和 GUIDED_LOCAL_SEARCH，不是 CP-SAT；限时解没有全局最优保证。贪心可行解是比较基线，不是目标函数下界。[OR-Tools 文档](https://developers.google.com/optimization/routing/routing_options)

6 个 Solomon 实例用于标准比较；新加坡算例为 **19 个节点**（1 个主仓、1 个第三方仓作对照、14 个医院收货点＝11 公立＋3 私立、3 个分拨点）与真实 OSM 有向矩阵（19×19，342 条有向路径），距离为 km、时间为 min。时间是自由流估计，不含实时拥堵。需求、车队及服务窗口均为模拟假设，不表示设施间存在真实业务关系；分拨点为零售门店的**模拟前置仓角色**，不具备医药冷链能力。

在线模式下 Vue 按已结案案例实时求解并展示路线，离线或未结案时回退预计算演示路线；温度变化本身不触发重求解。单仓补发单到求解器的映射已于 2026-09-12 落地，并可按「一组目的地 + 数量 + 时间窗」的订单形式通过 HTTP 调用。替代库存选择、多温区、碳排放和报废损失目标列为扩展。遗传算法仅在主链验收后考虑，不作为必交算法。

### 6.5 知识图谱与问答

Neo4j 图谱包含 Product、Regulation、SOP、ExcursionEvent、Disposition、Cause、Facility、Shipment、ReshipmentOrder 等实体。法规、公开程序性指引、产品配置、新加坡设施与数据集记录保留来源语义。Kaggle 的约 8,000 条运输级记录真实性未确认、疑似合成，不称为真实药企运输记录；匿名区域不能直接映射到新加坡医院。

case_close 保存记录并尝试写入图谱，decide 预览不归档。Cause 目前来自 API 启发式原因代码，不是 ML 推断或调查证实的根因。补发节点记录的是订单；该订单是否已求解、是否已执行，由调度运行状态（dispatch run state）追踪，不由图谱节点表达，且本流程任何一步都不代表发生了实际运输动作。日志与图谱均采用尽力保存，尚不具备审计级持久性保证。

Python 已有按 run_id 查询处置理由、审计链、产品要求及统计的函数；`/api/qa` 已实现为受限意图识别 + 参数化 Cypher，返回本次案例的证据，并区分无案例、证据不足、不支持的问题和数据库故障——这是结构化的问句类型路由，不是自然语言分类。Vue 客户端在线模式调用该端点，离线时回退到关键词模板。2026-09-13 已完成：响应带机器可读的 `status`（`ok` / 无案例 / 证据不足 / 不支持的问题；数据库故障仍以 503 表达），前端按状态渲染本地化提示；补发单与补发目的地已进入审计链的证据与答案；「该原因最常见场景」由本案例主因码聚合全部结案的 stage/product 分布；并修正 `CITES` 原先挂在共享 `Disposition` 节点上、导致同处置不同规则的案例互相串证据的缺陷（现为案例级 `(ExcursionEvent)-[:CITES]->(Regulation)`）。问答评估集与评测脚本见 `data/qa/` 与 `scripts/evaluate_qa.py`：57 条场景上 466/466 派生检查通过（期望值取自静态映射与 `rules_config.json`，非循环验证），意图分类准确率待人工标注。数据库链路已于 2026-09-13 在 `docker compose` 启动的 Neo4j 上完成端到端验证（结案 → 写图谱 → 按案例查证据，证据集合与触发规则的法规/SOP 映射逐条一致）。**仍未完成**：结案表单尚未传异常地点（补发目的地已传）；重复结案尚无去重。评估要求证据与具体规则匹配，不能以“有法规链接”代替验证。LLM 不属于 MVP 必需组件。

### 7.2 领域知识来源

规则依据来自 WHO、EU GDP、ICH 及适用产品资料；程序性节点引用 CDC/WHO 公开指南，不冒充企业内部 SOP。记录来源、适用范围和假设，逐步分开产品级证据与通用原则。尚未完成的规则复核不表述为“全部已验证”。

### 7.3 预处理与任务边界

- 各数据按原粒度单独建模，不虚构共有批次 ID 拼接运输、设施月度与新加坡订单。
- 无时间戳的失效任务使用分层随机划分；多折实验在每折训练部分完成预处理与阈值选择，测试部分仅用于最终评分。
- 设施月度任务检查重复实体及分组/时间划分可行性，报告相对随机划分的变化。
- 序列任务先定义产品温区、窗口、缺失处理、MKT 参数和预测时点，防止同批次重叠窗口跨集合泄漏。
- 当前演示导出按温度推断类别、以单点读数近似 MKT、将包装固定为完整；这些映射不用于验证真实产品稳定性或 MKT 算法。
- 阈值派生标签只检查事件提取逻辑，不用于证明采用相同阈值的处置规则具有独立领域正确性。
- OSMnx 从缓存道路生成有向距离/时间及同路径几何，保留来源指纹；订单和车辆假设单独记录。

## 8. 实验与评估

### 8.1 指标与验收

| 模块 | 指标与检查 | 结论边界 |
|---|---|---|
| 风险分类 | F1、ROC-AUC、PR-AUC、精确率/召回率、多折均值与标准差 | 不报告未定义的提前预警指标 |
| 处置规则 | gold 一致率、macro-F1、各类召回、混淆矩阵、κ、规则覆盖 | 分开实现符合规则、人工一致性与领域有效性 |
| 补发动作 | 补发政策一致性、订单生成与重复触发 | 与四类处置分别验收 |
| 候选原因 | Top-1、Top-3、macro-F1、支持数、失败案例 | 仿真分类不等于因果诊断 |
| 路线优化 | 距离、车辆数、合计时长、准时率、未服务、违规、运行时间 | 同实例、同约束、固定预算比较 |
| 图谱问答 | 正确率、案例相关证据覆盖、无证据拒答率、响应时间 | 引用数量不等于证据相关性 |
| 系统 | 端到端时延、标识关联、快照完整性、异常恢复 | 分开规则预览、求解和结案耗时 |

路线评估同时报告未服务订单，避免已服务客户的准时率掩盖失败。对比 Solomon 已发表解前需对齐车辆数目标、距离精度和约束；单个新加坡算例不证明运营节约。系统验收覆盖需补发、不需补发、无可行路线、无证据、服务故障及重复结案。

### 8.2 基线与阶段结果

下表风险结果于 2026-09-13 用 `scripts/train_risk_full.py` 在 `requirements.txt` 记录的仓库环境中复跑得到（seed 42）。数据疑似合成，结果只描述该数据集，不证明真实世界有效性；当前为单次随机划分，尚非多折结果。

| 风险模型（可解释特征） | 验证集阈值 | F1 | ROC-AUC | PR-AUC |
|---|---:|---:|---:|---:|
| 逻辑回归 | 0.55 | 0.626 | 0.891 | 0.651 |
| LightGBM | 0.50 | 0.691 | 0.925 | 0.754 |
| XGBoost | 0.45 | 0.685 | 0.922 | 0.731 |

原因实验中，LightGBM 的 Top-1=0.143、Top-3=0.421、macro-F1=0.125；多数类基线 Top-1=0.161、Top-3=0.284、macro-F1=0.028。Top-1 未超过多数类，结果支持继续研究候选排序和特征定义，不支持宣称可靠根因识别。正式版本需定义无歧义的 Top-3 基线及并列概率处理。

新加坡算例的 2026-09-10 已记录结果：

| 算法 | 使用车辆 | 服务客户 | 总距离 km | 合计路线时长 min | 违规 / 未服务 |
|---|---:|---:|---:|---:|---:|
| 贪心 | 2 | 10 | 142.6305 | 364.6972 | 0 / 0 |
| OR-Tools Routing（10 秒） | 2 | 10 | 133.8073 | 357.5731 | 0 / 0 |

距离减少约 6.19%。算例提供 3 辆车、各容量 200 单位；医院各需求 30 单位，窗口 09:00–17:00、服务 15 分钟；仓库 08:00–18:00。合计路线时长是各车工作时长之和；限时结果可能随环境变化。[实验进度](../PROGRESS.md)、[新加坡说明](../docs/singapore_network_assumptions.md)

### 8.3 处置决策 Ground-truth

57 个合成场景由 B/C 仅依据书面 rubric 独立全量标注、A 仲裁。2026-09-12 人工 gold 已替换引擎自产的占位标签。标注者是团队成员，不称为领域专家。原始个人作答保留于私有标注包，仓库保存仲裁标签、结论及指纹。

| 指标 | 当前结果 |
|---|---|
| B/C 原始一致条数 | 44/57 |
| 标注者间 Cohen's κ | 0.6434，未达到原定 0.80（仅度量 B↔C；rubric v1.1 未重标，故 κ 不变） |
| 当前引擎与 gold 一致 | 54/57，94.7%（rubric v1.1，2026-09-14；rubric v1 下为 39/57，68.4%） |
| 残留差异 | 3 条「gold 侧待复核」（S034/S035/S052：gold 均为隔离，引擎分别为放行、放行、复检）；rubric v1.1 一次消解原 15 条「引擎隔离/gold 报废」 |
| Gold 数量 | 放行 13、复检 8、隔离 3、报废 33 |
| 高后果类别召回 | 隔离 0/3；报废 33/33（100%） |

团队决定如实报告 κ=0.6434，不为提高 κ 修订 rubric 重测，保留 gold 中 3 条隔离。第 4 条的隔离/报废二选一已由 rubric v1.1 于 2026-09-14 定为 `scrap`，引擎与冻结测试同批更新，**故不再是未决政策**；该档背后的低温条证据缺口仍未闭合，`quarantine` 在 rubric 与引擎中均不再产出，gold 中 3 条历史值保留。隔离仅 3 条，各类结果需连同支持数报告，不作稳定总体性能推断。

评估分三层：单元测试检查实现符合冻结规则；人工 gold 检查书面规则与团队判断的差异；领域有效性需要适用产品资料或外部复核。测试冻结已知 3 条差异，测试通过不代表一致率 100%，也不证明这些差异均应通过改引擎解决。

本次修订直接运行真实引擎复核了 rubric v1.1 下的 54/57 及对应混淆计数。evaluate_engine.py 的 selftest 用 rubric 充当替身引擎，只校验脚本，不能作为性能证据。正式评估仍需输出完整 macro-F1、各类精确率/召回率、κ 和覆盖表，保留版本信息。[标注统计](../data/processed/agreement_stats.md)、[标注发现](../docs/annotation_findings_v1.md)、[引擎检查](../tests/test_rule_engine.py)

外部产品级复核为可选工作，尚未完成。后续如因领域证据修订规则，应版本化并用独立新增案例评估，不把对同批 gold 的调优当作新的独立验证。

## 9. MVP 与范围控制

**必须交付：**4 个明确标为原型的类别配置；四类处置与独立补发语义；单仓新加坡模拟配送；规则到补发单和路线的连接；真实 KG 查询到前端的接线；案例关联记录；独立规则评估、离线风险与原因实验；中英文界面及复现说明。

**补充目标：**序列事件生成与 MKT 验证、更多路由实例、更严格的数据划分。进度受限时优先完成必交闭环，披露演示输入近似，不把未实现的补充目标算作已交付。

**可选扩展：**提前预警、多级稳定性窗口、多仓库存选择、多温区优化、遗传算法、实时车辆位置、LLM 润色和反馈学习。扩展以主链验收为前提。

**明确排除：**生产 ERP/WMS、真实 IoT 部署、临床验证或正式合规认证、患者数据、自动授权实际药品处置及实际运输执行。

## 11. 风险与缓解

| 风险 | 缓解与披露 |
|---|---|
| 工程阈值误作稳定性界限 | 标注证据层级、产品适用性与假设，保留人工复核 |

## 13. 结论

PharmaColdOps 已具备规则决策核心、独立人工标注、离线实验和真实新加坡道路上的配送求解。结果同时揭示规则理解分歧、原因分类能力有限、数据真实性与产品阈值证据不足等限制，将指导后续验证。

剩余重点是接通补发需求、配送结果与案例证据，在 2026-10-25 前交付可解释、可复现、披露适用边界的最小闭环。项目以集成和评估展示 IRS 四类技术，不以未经验证的临床、运营或合规收益作为完成标准。
