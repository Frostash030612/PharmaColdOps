## 0. 背景 / 现状（写代码前必须知道的事实）

- 后端已经真实现（不是这次的工作）：`POST /api/route`（`RouteIn{run_id, algorithm}` → `RouteOut{order_id, algorithm, vehicles_used, total_distance, on_time_rate, routes}`）、`POST /api/qa`（`QAIn{question_type, run_id?, product_id?}` → `{answer, evidence}`）。参见 [src/api/schemas.py](../src/api/schemas.py)、[src/api/service.py](../src/api/service.py) 的 `route_view` / `qa_view`。
- 前端双模式的判断中枢是 `stores/decisions.js` 里的 `useApi` / `apiUp`（[decisions.js:32-33](../frontend-vue/src/stores/decisions.js#L32)）：`useApi` 由 URL 的 `?api=` 参数决定，`apiUp` 是健康检查结果。**任何新代码要判断"是否走真数据"都复用这两个字段，不要新造一套判断逻辑。**
- `ReroutePanel.vue`（[frontend-vue/src/components/ReroutePanel.vue](../frontend-vue/src/components/ReroutePanel.vue)）现在**完全无视** API 模式，永远读静态文件 `data/singaporeRoutes.json`。
- `QAPanel.vue` + `lib/qa.js`（[QAPanel.vue](../frontend-vue/src/components/QAPanel.vue)、[lib/qa.js](../frontend-vue/src/lib/qa.js)）现在是纯前端关键词匹配，同样无视 API 模式。
- **关键缺口**：`stores/sandbox.js` 的 `restoreCase(record)`（[sandbox.js:96](../frontend-vue/src/stores/sandbox.js#L96)）只取 `record.event` / `record.spec`，**把 `record.run_id` 丢掉了**。`/api/route` 和 `/api/qa` 的 `why_disposition`/`audit_chain` 都需要 `run_id`，这一步不补，后面全部接不上——**必须先做 §1，再做 §2/§3**。
- **一个真实的数据字段缺口**：`route_view()` 目前只序列化了 `vehicles_used / total_distance / on_time_rate` 三个字段（[service.py 的 `route_view`](../src/api/service.py)），但 `ReroutePanel.vue` 现有的指标格子还要显示 `served_customers` 和违规计数（`time_window_violations` 等），这些数字其实都在 `ReplanMetrics`（[optimisation/models.py:108](../src/optimisation/models.py#L108)）里，只是没有被序列化出来。**§1.5 先把这个字段缺口补上**，否则前端就算接完线，这两个格子也没数据可显示。
- **实现时补出的地图字段缺口**：草案中的实时 `plan` 没有 `geojson`，但 `LeafletMap.vue` 会读取 `plan.geojson.features`。仅靠静态节点无法还原新求解站序对应的道路。因此最终 `RouteOut` 还需返回由同一求解结果生成的 `geojson`；这不是新设施接口，也不会把全岛路网发给浏览器。
- **设计前提**：`data/optimisation/singapore/network.json` 与前端静态文件 `frontend-vue/src/data/singaporeRoutes.json` 用的是**同一套 `node_id` 编号**（后者由 `scripts/export_singapore_routes.py --frontend-out` 从前者生成）。这意味着**不需要新开一个接口查设施名字/坐标**——不管路线数据来自静态文件还是 `/api/route`，永远用现成的 `data.nodes` 数组做"查名字/坐标/时间窗"的字典，只是"该走哪条路线"这一份数据切换来源。这是本方案能不额外扩大后端范围的关键。

## 2. `/api/route` → `ReroutePanel.vue`

### 2.1 路线结果缓存（新增 store 状态）

**放在哪**：加进 `stores/decisions.js`（不新建 store——路线缓存跟 `grid` 缓存性质一样，都是"服务端结果，按 key 判断新鲜度"，放一起维护成本最低，参照现成的 `grid` / `gridKey` / `gridPending` 三件套写法）。

```js
// state 区新增：
const routeResults = ref({});   // { [`${runId}|${algorithm}`]: RouteOut }
const routePending = ref(new Set());

// 方法区新增：
function fetchRoute(runId, algorithm) {
  const key = `${runId}|${algorithm}`;
  if (routeResults.value[key] || routePending.value.has(key)) return;
  if (!useApi.value || apiUp.value === false) return;
  routePending.value.add(key);
  postJson(apiBase.value + "/api/route", { run_id: runId, algorithm })
    .then((res) => {
      apiUp.value = true;
      routeResults.value = { ...routeResults.value, [key]: res };
    })
    .catch(() => { /* 静默失败：面板自己判断 routeResults 里有没有这个 key，没有就回退静态数据 */ })
    .finally(() => routePending.value.delete(key));
}
```

`return {}` 导出列表加 `routeResults, routePending, fetchRoute`。

**为什么不用现成的 `syncDecision`/`syncGrid` 模式（防抖 watcher）**：路线请求不是每次滑杆微调都要重新拉，而是"进了这个面板 + 有一个已结案的 run_id + 用户点了 greedy/ortools 切换按钮"才需要，触发点在组件里手动调用 `fetchRoute`，不需要跟 `liveDecisionKey` 那样的响应式 watcher。

## 3. `/api/qa` → `QAPanel.vue`

### 3.1 关键词粗分类（新增函数，不是 NLP）

**文件**：`frontend-vue/src/lib/qa.js`，新增一个函数（保留原 `askKG` 不动，离线兜底继续用它）：

```js
/* Coarse keyword → structured question_type routing (client-side, per the
   /api/qa contract: real NLP classification is explicitly out of scope).
   Returns null when nothing matches — caller falls back to askKG(). */
const TYPE_KEYWORDS = {
  why_disposition: ["为什么", "依据", "why", "隔离原因", "判定原因"],
  audit_chain: ["链路", "追溯", "audit", "全过程", "chain"],
  product_requirements: ["阈值", "储存要求", "threshold", "requirement", "允许时长"],
  disposition_stats: ["统计", "分布", "多少例", "stats", "比例"],
};

export function classifyQuestion(q) {
  const s = q.toLowerCase();
  for (const [type, kws] of Object.entries(TYPE_KEYWORDS)) {
    if (kws.some((kw) => s.includes(kw.toLowerCase()))) return type;
  }
  return null;
}
```

### 3.2 `QAPanel.vue` 改造

```js
<script setup>
import { ref, computed } from "vue";
import { askKG, classifyQuestion } from "../lib/qa.js";
import { useDecisionsStore } from "../stores/decisions.js";
import { useSandboxStore } from "../stores/sandbox.js";
import { postJson } from "../lib/api.js";
import { locale, bundle } from "../i18n/index.js";

const decisions = useDecisionsStore();
const sandbox = useSandboxStore();
const L = computed(() => bundle(locale.value));
const q = ref("");
const answer = ref("");
const evidence = ref([]);   // [{node_type, node_id, summary}]

function ask() {
  const text = q.value.trim();
  if (!text) return;
  evidence.value = [];
  const type = classifyQuestion(text);

  if (!type || !decisions.useApi || decisions.apiUp !== true) {
    answer.value = askKG(text, L.value);
    return;
  }
  if ((type === "why_disposition" || type === "audit_chain") && !sandbox.currentRunId) {
    answer.value = L.value.right.qaNeedsCase;   // 新 i18n key，见 §4
    return;
  }
  const body = { question_type: type };
  if (type === "why_disposition" || type === "audit_chain") body.run_id = sandbox.currentRunId;
  if (type === "product_requirements") body.product_id = sandbox.current.product_id;

  postJson(decisions.apiBase + "/api/qa", body)
    .then((res) => { answer.value = res.answer; evidence.value = res.evidence || []; })
    .catch(() => {
      // 503（图库挂了）或网络问题：退回离线关键词表，但必须声明这不是真查询
      answer.value = askKG(text, L.value) + " " + L.value.right.qaOfflineNote;
    });
}
function onKeydown(e) { if (e.key === "Enter") ask(); }
</script>

<template>
  <div>
    <div class="qline">
      <input type="text" v-model="q" :placeholder="L.right.qaPlaceholder" @keydown="onKeydown">
      <button @click="ask">{{ L.right.qaAsk }}</button>
    </div>
    <div class="answer">{{ answer || L.right.qaInitial }}</div>
    <ul v-if="evidence.length" class="qa-evidence">
      <li v-for="(e, i) in evidence" :key="i">{{ e.node_type }}: {{ e.node_id }} — {{ e.summary }}</li>
    </ul>
  </div>
</template>
```

（`.qa-evidence` 样式沿用 `EvidencePanel.vue` 已有的 chip/list 样式约定，具体 class 名执行时对照那个文件抄，不要重新发明一套视觉语言。）

## 5. 测试要求

这个仓库的 `frontend-vue/` 从来没有 JS 单元测试框架（历次 PROGRESS 记录里前端验证方式都是"`npm run build` 通过 + 浏览器手测"），**这次不引入新的测试框架**，沿用这个惯例：

1. `npm run build`（或 `pnpm build`，本仓库已统一 pnpm）必须过。
2. 后端：`pytest -q -k route` 确认 §1.5 的字段补全没有破坏现有测试，且新断言通过。
3. 浏览器手测清单（照抄到位即可，不需要脑补新场景）：
   - 离线模式（不带 `?api=`）：路线面板和问答框行为跟改动前逐字节一致——这是最容易被破坏又最容易漏测的一条，必须先测。
   - 在线模式，**未结案**（`currentRunId` 为空）：路线面板显示固定演示路线 + "固定演示路线"文案；问答框问"为什么判定"类问题得到"请先结案"提示；问产品阈值类问题正常查到真答案（这条不需要 `run_id`）。
   - 在线模式，**结案一个 `scrap`/`quarantine` 场景**（比如冻结场景）：路线面板自动切到真实路线 + "当前案例真实路线"文案，greedy/ortools 切换都能各自取到数据；问答框问"为什么隔离"能拿到真实 `why_disposition` 答案 + evidence 列表。
   - 在线模式，**结案一个 `release` 场景**：路线面板应保持"固定演示路线"（因为 `decisionFor.reshipment` 为假，`canUseLiveRoute` 应为假）——这条断言的是 §2.2 的判断条件写对了没有，容易漏。
   - 把后端进程杀掉再问一次问题：问答框应该退回离线关键词表 + 显示"离线示意"字样，不能报错崩掉。

## 8. 调度约束输入（2026-09-16，B3）

`ReroutePanel.vue` 的今日批次区新增一组「调度约束」控件，直接对应
`POST /api/dispatch/plan` / `/runs` 的 `constraints`（字段语义见 [接口契约.md §9.5](接口契约.md)）：

| 控件 | store 字段 | 说明 |
|---|---|---|
| 车队上限 | `constraintsForm.max_vehicles` | 全系统车辆数 |
| 每车里程上限（km） | `constraintsForm.mileageLimitKm` | **字符串**：留空 = 不限（提交时转成米，空为 `null`） |
| 每车最多站点 | `constraintsForm.max_stops_per_vehicle` | — |
| 可作终点站（多选） | `constraintsForm.terminal_facility_ids` | 选项 = `singaporeRoutes.json` 里 `role !== "customer"` 的节点（主仓/第三方仓/分拨点）；**空选 = 全部回主仓** |

**接线纪律**：预览（`previewDailyPlan()`）与建单（`confirmDailyPlan()`）都经 `planBody()` 组装请求体，
不得各写一份；`absorbConstraints()` 只在操作员未改动时吸收后端默认值，避免"换批次把用户设的上限冲掉"。

**回显**：约束条 + 每条路线的「收车于 <终点站> · X km」+ 未服务订单红字说明，三者都来自
服务端响应（`zones[].terminal_facility_ids` / `mileage_violations` / `routes[].end_facility_id`），
前端不自行推算。
