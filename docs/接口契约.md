## 1. `ReshipmentOrder`（Python 数据类，新增）

**文件**：`src/optimisation/models.py`（追加到已有的 dataclass 之后，不要新建文件——`ReplanResult` 也在这里，两者天然是一对）

```python
@dataclass(frozen=True)
class ReshipmentOrder:
    """A resupply request derived from one closed disposition case.

    Bridges src/rule_engine (Decision.reshipment_required) to src/optimisation
    (VRPTW solvers). Mirrors the Neo4j :ReshipmentOrder node written by
    src/knowledge_graph/writer.py (order_id = f"RO-{run_id}") — do not invent
    a different id scheme, the two must stay joinable by order_id.
    """

    order_id: str            # "RO-{run_id}", same id the KG writer uses
    run_id: str               # source case's run_id (audit trail back to /api/case_close)
    product_id: str
    origin_facility_id: str   # where the excursion happened / nearest depot — see §2 rule
    destination_facility_id: str  # resolved delivery target — see §2 rule
    demand_units: int         # replacement shipment size; fixed default, see §2
    priority: str             # "scrap" | "quarantine" — mirrors Decision.disposition
    requested_at: str         # ISO timestamp, copied from the case's created_at
```

字段来源对照表（不得改名、不得新造别名）：

| 字段 | 来源 |
|---|---|
| `order_id` | `f"RO-{run_id}"`，与 `writer.py:73` 的 `order_id` 公式**完全一致** |
| `run_id` | `close_case()` 返回记录的 `run_id` |
| `product_id` | `record["event"]["product_id"]` |
| `priority` | `record["disposition"]`（只有 `scrap`/`quarantine` 会走到这里，因为只有这两类 `reshipment_required=True`） |
| `requested_at` | `record["created_at"]` |
| `origin_facility_id` / `destination_facility_id` | 见 §2 的解析规则——**当前 case 契约里没有这两个字段**，需要在 §2 里定义一个合理默认，不是从请求里读到的 |

## 2. 补发单 → 仓库/目的地解析规则（新函数，MVP 版本，明确写死假设）

**背景事实**：`EventIn`（[src/api/schemas.py:23](../src/api/schemas.py#L23)）目前只有 6 个字段（`product_id, excursion_temp_c, duration_min, mkt_c, packaging, stage`），**没有地点字段**。`writer.py` 已经预留了 `facility_id` / `destination_facility_id`（[service.py:269](../src/api/service.py#L269) 的 `_event_dump` 会透传，如果 `EventIn` 上有这两个字段的话），但 `EventIn` 本身没声明它们。

**这次要做的决定**（写进代码注释，不要含糊带过）：

1. 给 `EventIn` **新增两个可选字段**：`facility_id: Optional[str] = None`（异常发生地）、`destination_facility_id: Optional[str] = None`（指定补发目的地，可选）。这样：
   - 前端/调用方如果知道地点就传，`_event_dump` 已经会自动透传给 KG writer（代码已经写好，只是字段没在 schema 里声明，加上就生效）。
   - 不传时，路线模块要有默认兜底逻辑（见下）。
2. **仓库/depot 固定**：MVP 阶段只有一个 depot（`W-KN-PIONEER`），`origin_facility_id` 恒等于这个 depot 的 `facility_id`，不做多仓库选择逻辑（多仓库是 W4+ 的范围，不在这次任务里，DAILY_PLAN 里也没排）。
3. **目的地解析**：
   - 若请求带了 `destination_facility_id` 且该 id 存在于 `network.json` 的 `nodes` 里 → 直接用。
   - 若没带 → 默认选 `network.json` 里 `role == "customer"` 的**第一个**节点（写代码时用列表里第一条，不做"最近"之类的智能匹配——这是 MVP，智能选址不在范围内，写进 docstring 说明白）。
4. **`demand_units` 固定为 1 个单位的补发批次**（对应 `network.json` 里医院节点的 `demand: 30`，这里的 30 是当前 Solomon 风格演示数据的固定需求量，直接沿用，不新造数字）。

def plan_reshipment_route(
    order: ReshipmentOrder,
    *,
    algorithm: str = "greedy",   # "greedy" | "ortools"
    network_path: str | Path = SINGAPORE_NETWORK_PATH,

    """order → load network → pick solver → ReplanResult.

    Does NOT create a new one-order VRP instance per call — MVP reuses the

**诚实边界（必须写进代码注释和 PROGRESS）**：这个 MVP **不会**为一张补发单单独重新求解一个只含这一个目的地的路线；它复用现成的、已验证过的新加坡固定算例（1 depot + 10 医院），校验补发单的目的地在这个算例里，然后跑一次全量 `solve_greedy`/`solve_ortools`，把结果当作"这张单所在的改派方案"返回。如果目的地不在算例的 10 个节点里，返回明确错误（`ValueError`），不要静默兜底成别的节点。

**文件**：`src/api/service.py`（新增函数 `route_view`）

def route_view(req: RouteIn) -> dict:

    404 (via ValueError caught in main.py) when run_id is unknown or the case

实现要点：

from knowledge_graph import qa as kg_qa  # noqa: E402  (import at module top, follow existing pattern)

def qa_view(req: QAIn) -> dict:
    """Route to the matching kg_qa function; Neo4j-down errors surface as 503, not 500.

    2026-09-13: an intent outside the four supported ones returns
    status="unsupported" instead of falling through to disposition_stats().
    """
    try:
        if req.question_type == "why_disposition":
            return kg_qa.why_disposition(req.run_id)
        if req.question_type == "audit_chain":
            return kg_qa.audit_chain(req.run_id)

        if req.question_type == "disposition_stats":

        return kg_qa.unsupported_response(req.question_type)

## 9. `GET /api/dispatch/daily-orders`（今日配送计划的订单来源，2026-09-14 新增）

**为什么需要它**：`POST /api/dispatch/runs` 的 `orders` **本来就是数组**、`plan_delivery_orders()`
**本来就会一车串多站**，但运行中的系统只有「结案 → 补发」一条入口，而
`service.route_reshipment()` 每次只规划**一张**单（`plan_delivery_orders((order,), …)`），
于是每辆车只去一家医院、多站排线在运行时**从未被触发过**（`docs/C_配送模块.md` §3.2／§4.1）。
本端点补上「一批日常订单从哪来」。

**请求**：`GET /api/dispatch/daily-orders?hospitals=4&seed=&temperature_zone=chilled`

| 参数 | 默认 | 说明 |
|---|---|---|
| `hospitals` | 4 | 本批医院数；范围 1…网络客户数，越界 → 422 |
| `seed` | 无 | 给了就用**可复现的随机抽样**；**不给就是固定演示集**（前 N 家，答辩与报告数字稳定）|
| `temperature_zone` | `chilled` | `chilled`／`frozen`／`ultracold`；未知 → 422 |

**响应**：`{ note, seed, hospitals, temperature_zone, plan }`，其中 `plan` **就是**
`POST /api/dispatch/plan` 的请求体，客户端预览后再补 `dispatch_id` + `command_id` 提交给
`POST /api/dispatch/runs`。本端点**不持久化任何东西**。
客户端自行生成作业号 `PLAN-<epoch 秒>`（`_run_sequence` 认尾部数字，故排序仍正确）。

**模拟数据边界（不得含糊）**：医院身份、收货窗口、服务时长、需求量取自
`data/optimisation/singapore/network.json`（真实设施 + 已声明的演示需求量）；产品组合与车队规模
是本项目假设。响应里的 `note` 与前端文案都必须写明这一点，不得让演示看起来像真实医院订单。

**`GET /api/dispatch/active` 的语义变更（同批）**：原先只认 `RESHIPMENTS-` 前缀（补发路径独占），
现改为按「**最近被写入的作业**」解析，因此 `PLAN-…` 这类今日计划作业也能被面板看到；
