## 0. 背景 / 现状（写规格前必须知道的事实）

**2026-10-01 作业执行与跨天契约**：每条调度路线回显 `start_node_id` / `start_facility_id` / `start_time_min`，
执行视图回显实际收车点和 `distance_driven_m`。地图、交付时钟与应急评估共用车辆日程；不可行候选提供 `blocked_by`。

| 作业端点（均为 POST `/api/dispatch/runs/{id}/...`） | 请求与行为 |
|---|---|
| `overnight-preview` | `{parking_overrides?: {vehicle_id: facility_id}, replenishments?: InventoryLotIn[], tomorrow?: DispatchPlanIn}`。固定订单可另行提供；库存始终取当前剩余可用批次加明确登记的新批次。返回 `state_version`、停车建议、当日位移／约束检查和实际车位下的次日方案 |
| `overnight-accept` | 同一预览输入加 `expected_version`、`command_id`。重验后确认停车位移，状态为 `repositioning` 或无需位移时直接 `parked`；完成交付及收尾前拒绝 |
| `next-day` | `{dispatch_id, command_id, expected_version, depart?: true, speed?: 60}`。全部停妥才可建单，日期递增、车位及随车余货继承、每日里程重置；重复命令返回既有子作业 |

停车点须在允许集合（或保持原位），新增供货批次须唯一、可用、正数量且与供货点／产品温区匹配。
确认／建单的冲突返回 409；未知作业返回 404。原 `/api/dispatch/overnight-plan` 仍是独立只读分析。

- **当前实现**：`POST /api/route` 是已结案补发案例的无资源预留路线预览；
  `POST /api/qa` 是结构化问题类型到案例级 Neo4j 证据的查询；
  `POST /api/dispatch/reshipments` 才会预留库存并把候选方案写入进行中的配送作业。
- **2026-09-30 故障救援**：`POST /api/dispatch/runs/{id}/failure-preview` 只读评估
  故障车的未完成订单能否由备用车用替代库存完成；`failure-accept` 才写入状态。当前
  v1 不假定车对车或冷藏设施转运能力，故障车货物视为不可用。
- **2026-09-30 延误巡检**：每次 `tick` 在结算交付后返回 `delay_inspection`（仅扫描，
  不自动换序）。`POST /api/dispatch/runs/{id}/delay-preview` 提供完整重排比较，请求示例
  `{ "delay_min": 10 }`；可选 `current_time_min` 默认取作业时钟。响应含 `state_version`、
  `candidates[].remaining_order_ids_after`、原/新迟到指标、逐单 ETA 和道路几何。
  `delay-accept` 需提交 `vehicle_id`、`command_id`、`expected_version`（来自预览的
  `state_version`）和选中的 `remaining_order_ids_after`，并携带同一 `delay_min`。
  接受时按最新作业时刻重新核验；版本或候选变化返回 409，重复命令幂等。车队状态与
  `delay_replans` 审计记录在同一事务持久化。v1 保护原本准时的订单，校验整车里程及收车窗口；
  PDPTW 显式取送计划和含取货绕路的作业返回明确的能力边界（预览 422）。
- `ReshipmentOrder` **已经**是一个 Neo4j 图节点：`close_case` → `write_case()`（[src/knowledge_graph/writer.py:124-141](../src/knowledge_graph/writer.py#L124)）在 `reshipment_required=True` 时会 `MERGE (ro:ReshipmentOrder {order_id: f"RO-{run_id}"})`，并预留了 `destination_facility_id` 字段的写入位置（目前恒为空，因为没人产出这个字段）。
- `ReshipmentOrder` **没有** Python 侧的数据类/Pydantic model。`ReplanResult` 已经有（[src/optimisation/models.py:135](../src/optimisation/models.py#L135)），是 C 定义的路线结果。
- `src/knowledge_graph/qa.py` 已经有 4 个真实 Cypher 查询函数可直接复用：`why_disposition(run_id)`、`audit_chain(run_id)`、`product_requirements(product_id)`、`disposition_stats()`。
- 新加坡设施数据在 `data/optimisation/singapore/network.json`：**19 个节点**——1 个主仓（`W-WESTGATE`，`role: "depot"`）、1 个第三方仓（`W-KN-PIONEER`，`role: "third_party"`）、14 家医院（`role: "customer"`）、3 个分拨点（`D-NORTHPOINT` / `D-HOUGANG` / `D-BUGIS`，`role: "distribution"`）。字段：`facility_id, name, role, demand, earliest_min, latest_min, service_min, node_id, lat, lon`；凡 `role` 非 `customer` 者 `demand` 与 `service_min` 恒为 0（`validate_network` 会拒绝）。
- 求解器：`solve_greedy(instance, *, leg_fn=euclidean_leg) -> ReplanResult`（[greedy.py:46](../src/optimisation/greedy.py#L46)），`solve_ortools(instance, *, time_limit_seconds=10, leg_fn=euclidean_leg, first_solution="PATH_CHEAPEST_ARC", drop_penalty=0, minimize_vehicles=False) -> ReplanResult`（[ortools_solver.py:10](../src/optimisation/ortools_solver.py#L10)），`solve_ga(instance, *, leg_fn=euclidean_leg, seed=42, time_limit_seconds=10, population_size=60, max_generations=None) -> ReplanResult`（[ga_solver.py](../src/optimisation/ga_solver.py)）。三者都吃 `SolomonInstance`、都返回同一个 `ReplanResult`，跟 `load_singapore_instance()` 返回的类型一致（[singapore_loader.py:78](../src/optimisation/singapore_loader.py#L78)）。
  - 2026-09-14 新增/变更（口径以 `docs/C_配送模块.md` §5 A1–A3 为准）：`solve_ga` 为**纯标准库** GA（客户排列 + 顺序交叉 + 短程变异 + 最优 split 解码）；`solve_ortools` 的 `first_solution` 用于绕开默认首解策略在 r101/rc101 上构造失败的问题，`minimize_vehicles` 用每车固定成本把目标对齐 Solomon 的层级式口径（**不可与 `drop_penalty` 同时开启**，会返回空解，代码会直接拒绝）。
- Neo4j 用本地容器即可：仓库根执行 `docker compose up -d`（容器 `pharmacoldops-neo4j-1`，Bolt `neo4j://localhost:7687`，默认口令 `pharmacoldops`），载图 `python -m src.knowledge_graph.build_graph`。`/api/qa` 的代码要写对、要有测试；测试在 DB 不可达时**必须**优雅跳过或返回明确错误——不允许假装验证过真实查询结果。9/13 起容器可用，`needs_db` 用例会真实执行（`tests/conftest.py` 只在不可达或缺驱动时才 skip，并在 skip 原因里写明缺哪一样）。

## 1. `ReshipmentOrder`（Python 数据类，新增）

**文件**：`src/optimisation/models.py`（追加到已有的 dataclass 之后，不要新建文件——`ReplanResult` 也在这里，两者天然是一对）

```python
@dataclass(frozen=True)
class ReshipmentOrder:
    """A resupply request derived from one closed disposition case.

    Bridges src/rule_engine (Decision.reshipment_required) to src/optimisation
    (VRPTW solvers). Mirrors the Neo4j :ReshipmentOrder node written by
    src/knowledge_graph/writer.py (order_id = f"RO-{run_id}") — do not invent
    a different id scheme, the two must stay joinable by order_id.
    """

    order_id: str            # "RO-{run_id}", same id the KG writer uses
    run_id: str               # source case's run_id (audit trail back to /api/case_close)
    product_id: str
    origin_facility_id: str   # where the excursion happened / nearest depot — see §2 rule
    destination_facility_id: str  # resolved delivery target — see §2 rule
    demand_units: int         # replacement shipment size; fixed default, see §2
    priority: str             # "scrap" | "quarantine" — mirrors Decision.disposition
    requested_at: str         # ISO timestamp, copied from the case's created_at
```

字段来源对照表（不得改名、不得新造别名）：

| 字段 | 来源 |
|---|---|
| `order_id` | `f"RO-{run_id}"`，与 `writer.py:73` 的 `order_id` 公式**完全一致** |
| `run_id` | `close_case()` 返回记录的 `run_id` |
| `product_id` | `record["event"]["product_id"]` |
| `priority` | `record["disposition"]`（只有 `scrap`/`quarantine` 会走到这里，因为只有这两类 `reshipment_required=True`） |
| `requested_at` | `record["created_at"]` |
| `origin_facility_id` / `destination_facility_id` | 见 §2 的解析规则——**当前 case 契约里没有这两个字段**，需要在 §2 里定义一个合理默认，不是从请求里读到的 |

## 2. 补发单 → 仓库/目的地解析规则（新函数，MVP 版本，明确写死假设）

**历史方案背景**：下列文字记录了地点字段与默认目的地曾经如何设计。当前 `EventIn` 已可携带
`order_id`、`facility_id` 与 `destination_facility_id` 等可选字段；异常发生地尚未由结案表单采集，
目的地在前端由沙箱状态传入。字段定义以 `src/api/schemas.py` 为准。

**这次要做的决定**（写进代码注释，不要含糊带过）：

1. 给 `EventIn` **新增两个可选字段**：`facility_id: Optional[str] = None`（异常发生地）、`destination_facility_id: Optional[str] = None`（指定补发目的地，可选）。这样：
   - 前端/调用方如果知道地点就传，`_event_dump` 已经会自动透传给 KG writer（代码已经写好，只是字段没在 schema 里声明，加上就生效）。
   - 不传时，路线模块要有默认兜底逻辑（见下）。
2. **默认起点固定**：当前仍只有一个默认 depot（`W-WESTGATE`，`DISPATCH_ORIGIN`），`origin_facility_id` 恒等于它，**尚未实现按订单选起点**。3 个分拨点已入网（2026-09-16），但要用它们取货需要先补 `docs/路径规划总逻辑方案.md` §2.3 的供货表与订单 `origin_facility_id` 字段（B1 批次）。
3. **目的地解析**：
   - 若请求带了 `destination_facility_id` 且该 id 存在于 `network.json` 的 `nodes` 里 → 直接用。
   - 若没带 → 默认选 `network.json` 里 `role == "customer"` 的**第一个**节点（写代码时用列表里第一条，不做"最近"之类的智能匹配——这是 MVP，智能选址不在范围内，写进 docstring 说明白）。
4. **`demand_units` 固定为 1 个单位的补发批次**（对应 `network.json` 里医院节点的 `demand: 30`，这里的 30 是当前 Solomon 风格演示数据的固定需求量，直接沿用，不新造数字）。

## 4. `POST /api/route`（真实现）

**文件**：`src/api/schemas.py`（新增两个 model）

```python
class RouteIn(BaseModel):
    run_id: str                      # references a case already closed via /api/case_close
    algorithm: Literal["greedy", "ortools"] = "greedy"

class RouteOut(BaseModel):
    order_id: str
    algorithm: str
    vehicles_used: int
    total_distance: float
    on_time_rate: float
    routes: list[dict]                # one dict per VehicleRoute (customer_ids, stops summary)
```

**文件**：`src/api/service.py`（新增函数 `route_view`）

```python
def route_view(req: RouteIn) -> dict:
    """Look up the closed case by run_id, build its ReshipmentOrder, solve, serialise.

    404 (via ValueError caught in main.py) when run_id is unknown or the case
    was not reshipment_required — routing only makes sense for scrap/quarantine
    cases with reshipment_required=True.
    """
```

实现要点：
1. 从 `list_runs()` 里按 `run_id` 找到那条 record（`RUNS_FILE` 已有全部字段）——不要重新设计存储，复用现成的 `data/audit/runs.jsonl`。
2. 若 `record["reshipment_required"]` 为假 → 抛 `ValueError`（main.py 里接住转 404，写清楚 detail："case {run_id} does not require reshipment"）。
3. `build_reshipment_order(record)` → `plan_reshipment_route(order, algorithm=req.algorithm)` → 序列化成 `RouteOut`。

**历史实现目标**：`src/api/main.py` 的 501 stub 已于 2026-09-13 替换为真实端点。

```python
@app.post("/api/route")
def route(req: RouteIn):
    try:
        return service.route_view(req)
    except KeyError:
        raise HTTPException(status_code=404, detail=f"unknown run_id {req.run_id!r}")
    except ValueError as exc:
        raise HTTPException(status_code=422, detail=str(exc))
```

## 5. `POST /api/qa`（真实现）

**文件**：`src/api/schemas.py`

```python
class QAIn(BaseModel):
    question_type: str                 # 五种支持的意图见下；其余返回 status="unsupported"
    run_id: Optional[str] = None       # required for why_disposition / audit_chain；cause_context 亦可
    product_id: Optional[str] = None   # required for product_requirements
    cause_code: Optional[str] = None   # cause_context 可选；缺省时由 run_id 的案例主因推导
```

支持的五种意图：`why_disposition` · `audit_chain` · `product_requirements` · `cause_context`（「该原因最常见场景」：默认取本案例主因码，聚合全部结案的 stage/product 分布）· `disposition_stats`。

**响应契约（2026-09-13 起）**：`QAOut = {status, answer, evidence: [{node_type, node_id, summary}]}`，`status ∈ {ok, no_case, insufficient_evidence, unsupported}`；数据库故障仍是 HTTP 503。为此 `question_type` 由 `Literal[...]` 放宽为 `str`——不在四种意图内的提问返回结构化 `status="unsupported"` 而非 4xx，前端据此渲染本地化提示。`answer` 与 `evidence` 文本逐字引用来源文档（WHO/EU/CDC 英文原文与设施名），**只有状态提示**在前端做 i18n；翻译证据正文等于编造内容，不做。

**不做自由文本自然语言分类**——DAILY_PLAN D 组 9/18 原计划里有"问题分类 → 模板 Cypher"，但真正的分类逻辑（NLP/关键词匹配）超出这次任务范围。这次交付的是**结构化问题类型 + 直接路由到 `qa.py` 对应函数**，前端负责把用户点击的按钮/下拉选项映射成 `question_type`（前端已经有关键词匹配的 FAQ 逻辑，这次先不去碰它，只保证后端有真实现可切）。

**文件**：`src/api/service.py`（新增 `qa_view`，直接转调 `knowledge_graph.qa` 里的函数）

```python
from knowledge_graph import qa as kg_qa  # noqa: E402  (import at module top, follow existing pattern)

def qa_view(req: QAIn) -> dict:
    """Route to the matching kg_qa function; Neo4j-down errors surface as 503, not 500.

    2026-09-13: an intent outside the four supported ones returns
    status="unsupported" instead of falling through to disposition_stats().
    """
    try:
        if req.question_type == "why_disposition":
            return kg_qa.why_disposition(req.run_id)
        if req.question_type == "audit_chain":
            return kg_qa.audit_chain(req.run_id)
        if req.question_type == "product_requirements":
            return kg_qa.product_requirements(req.product_id)
        if req.question_type == "disposition_stats":
            return kg_qa.disposition_stats()
        return kg_qa.unsupported_response(req.question_type)
    except Exception as exc:  # Neo4j unreachable / query error — never leak a stack trace
        log.warning("qa query failed: %s", exc, exc_info=True)
        raise RuntimeError("knowledge graph unavailable") from exc
```

## 9. `GET /api/dispatch/daily-orders`（今日配送计划的订单来源，2026-09-14 新增）

**为什么需要它**：`POST /api/dispatch/runs` 的 `orders` **本来就是数组**、`plan_delivery_orders()`
**本来就会一车串多站**，但运行中的系统只有「结案 → 补发」一条入口，而
`service.route_reshipment()` 每次只规划**一张**单（`plan_delivery_orders((order,), …)`），
于是每辆车只去一家医院、多站排线在运行时**从未被触发过**（`docs/C_配送模块.md` §3.2／§4.1）。
本端点补上「一批日常订单从哪来」。

**请求**：`GET /api/dispatch/daily-orders?hospitals=4&seed=&temperature_zone=chilled`

| 参数 | 默认 | 说明 |
|---|---|---|
| `hospitals` | 4 | 本批医院数；范围 1…网络客户数，越界 → 422 |
| `seed` | 无 | 整数＝**可复现的随机抽样**；字面量 **`today`**＝按**当天日期**派生（同一天内可复现、跨天自动变——这是"像公司每日配送数据"的离线等价物，无需任何真实数据源）；**不传**＝固定演示集（前 N 家，答辩与报告数字稳定）。其他文本 → 422 |
| `temperature_zone` | `chilled` | `chilled`／`frozen`／`ultracold`；未知 → 422 |

**响应**：`{ note, seed, hospitals, temperature_zone, plan }`，其中 `plan` **就是**
`POST /api/dispatch/plan` 的请求体，客户端预览后再补 `dispatch_id` + `command_id` 提交给
`POST /api/dispatch/runs`。本端点**不持久化任何东西**。
客户端自行生成作业号 `PLAN-<epoch 秒>`。
> ↺ **2026-09-15 更正**：原文补了一句"`_run_sequence` 认尾部数字，故排序仍正确"——**这句是错的，且正是 bug 的来源**。
> 批次按钮生成的 `PLAN-<yyyymmdd>` 与控制台的 `PLAN-<epoch 秒>` 数字量级不同，
> 按"末尾数字最大"挑进行中的作业会挑到一条**已完成的**计划。现在一律按 `updated_at` 判定，与 id 命名无关
> （见 §9.2 与 `docs/C_配送模块.md` §10 第 12 条）。

**模拟数据边界（不得含糊）**：医院身份、收货窗口、服务时长、需求量取自
`data/optimisation/singapore/network.json`（真实设施 + 已声明的演示需求量）；产品组合与车队规模
是本项目假设。响应里的 `note` 与前端文案都必须写明这一点，不得让演示看起来像真实医院订单。

**`GET /api/dispatch/active` 的语义变更（同批）**：原先只认 `RESHIPMENTS-` 前缀（补发路径独占），
现改为按「**最近被写入的作业**」解析，因此 `PLAN-…` 这类今日计划作业也能被面板看到；
已完成（`completed`）的作业视为「没有进行中的作业」→ 404。
> ↺ **2026-09-15 更新**：本条末句"补发路径自己的 bootstrap 规则不变"**已作废**——补发路径的
> bootstrap 同日晚间被删除（见下 §9.2）。`active_reshipment_run()` 与 `RESHIPMENTS-` 前缀都不存在了。
配套修复：本地 SQLite 表原先没有 `updated_at` 列（只有 Postgres 建表语句里有），已按
`context_json` 的同一套轻量迁移补上；迁移前的旧行该列为 NULL，排序时落在新行之后。

## 9.2 支线事件：挂到当天计划上，并在提交前比较（2026-09-15）

**契约变更（有意识，非兼容）**：`POST /api/dispatch/reshipments` 不再 bootstrap 作业。

| 项 | 变更前 | 变更后 |
|---|---|---|
| 无进行中的作业时 | **自己建一条一单作业**（`RESHIPMENTS-N`） | **409** `no daily delivery plan is open…`，提示先建当天计划 |
| 挂到哪个作业 | 最近的 `RESHIPMENTS-` 作业 | 进行中的 **`PLAN-` 作业**（`active_plan_run()`：按 `updated_at` 取最近被动过且未完成的那条） |
| 响应字段 | `bootstrapped: true/false` | **`inserted: true/false`**，并回显 `candidate_kind` / `vehicle_id` |
| 批次外温区 | 用 `_bootstrap_fleet` 建一条新作业 | 就地给当天计划**补该温区的演示车队**（`_zone_fleet`），作业仍是同一条 |

**新端点**：`POST /api/dispatch/reshipments/preview`，请求 `{ run_id, policy? }`，**只读**。
响应 = 由案例派生的订单 + `preview_emergency_order()` 的全部候选：
`{ dispatch_id, order_id, order, already_committed, scheduled_next_day, policy, feasible,
selected_candidate, candidates[], limitations[] }`。
候选字段**统一**：`kind` / `vehicle_id` / `eta_min` / `on_time` / `lateness_min` / `distance_m` /
`affected_order_ids` / `affected_orders[]`（含 `baseline_eta_min` / `new_eta_min` / `delay_min` /
`already_late` / `newly_late`）/ `starts_new_vehicle`。无计划 → **409**（与提交端一致）。

**候选类型（`candidate_kind`）四选一**：

| kind | 含义 | 货从哪来 |
|---|---|---|
| `add_stop_in_transit` | 在途车**顺路加一站**，不回仓库 | 车上余货（`onboard_spare`），**须同产品同温区** |
| `load_before_departure` | 车还没发，装货时带上 | 仓库批次 |
| `return_to_depot` | 在途车折返仓库取货再送 | 仓库批次 |
| `spare_vehicle` | 另派一辆备用车 | 仓库批次 |

> ⚠️ `EmergencyAcceptIn.candidate_kind` 原先的字面量只列了 `spare_vehicle` / `return_to_depot`，
> 于是**预览给出了 `load_before_departure`、接受时却回 422**。现已按实现补齐四种。

**新请求字段**：

| 字段 | 出现在 | 说明 |
|---|---|---|
| `policy` | 上述三个端点 | `minimize_disruption`（默认，不影响在途订单优先）/ `minimize_vehicles`（省运力：优先复用已在跑的车）。未知值 → 422；响应回显所用口径 |
| `candidate_kind` + `vehicle_id` | `POST /api/dispatch/reshipments` | 可选：操作员从比较界面选定的方案。给了就按它应用（仍会重新校验，不可行则 409），不给则按 `policy` 自动选 |
| `onboard_spare` | `POST /api/dispatch/{plan,runs}` 的 `vehicles[]` | `[{product_id, temperature_zone, quantity}]`，车上余货。**装载假设**：占用额定载重（排线可用载重 = 额定载重 − 余货），不进批次台账；用余货服务订单时预留记为 `ONBOARD-<车号>` |

**兼容性**：`VehicleProgress` 新增 `onboard_spare`，旧持久化状态缺该字段时按"车上无余货"载入

另有两条**只影响实现**的修复记录在 `docs/C_配送模块.md` §10 第 12–14 条（"进行中的计划"选错、

## 9.3 地图运输视图所需的数据（2026-09-15 晚）

演示重点转到"在地图上看运输过程"后，界面需要三样此前没有的东西。**都是新增字段，不破坏既有消费方。**

**① 分腿几何：`route_view.routes[].legs`**

一次请求内每条线路的每一段：`{ from, to, node_id, order_id, delivered, coords }`，
按"仓库 → 各站（**含已送达**）→ 仓库"排列。第 i 段终点是第 i 站（末段是回仓，`order_id = null`）。
此前只有整条合并的 `geojson`（且**只含未送达站点**），所以画不出"哪一段已经走过"。
`geojson` 字段保持原样，`fit()` 之类的既有用法不受影响。

**② 候选方案的路线几何与代价：`/reshipments/preview` 与 `/emergency-preview` 的响应**

| 字段 | 位置 | 说明 |
|---|---|---|
| `node_sequence` | 每个候选 | 该方案下车要走的节点序列，**从车当前所在节点起算**（不是从仓库） |
| `route_geojson` | 每个候选 | 上述序列的 LineString，地图直接可画 |
| `sequence_distance_m` | 每个候选 | 该序列的总里程 |
| `added_distance_m` | 每个候选 | 相对"不改道继续走"多出的里程（另派车＝全程） |
| `baselines[vehicle_id]` | 响应顶层 | 该车**改道前**的 `{node_sequence, current_node_id, has_work, route_geojson, distance_m}` |

这就是 §4.3「扰动前后对比」的数据面：**没有它，那张图只能画数字**。

**③ `speed = 0` = 真暂停**

`POST /api/dispatch/runs/{id}/speed` 的 `speed` 放宽为 `ge=0`；`0` 冻结模拟时间
（`simulated_now` = 起始分钟 + 已过真实时间 × 速度，故 0 时恒定），恢复时以冻结的那一分钟重新起算。
`make_clock()` 的校验由"必须为正"改为"不能为负"。**语义区别**：这不是"停止刷新"——
停止刷新只是画面不动、时间照走；0 倍速是时间本身不走。
`depart` 也已接受 `speed`（此前接口模型里没有该字段，调用方传了会被静默丢弃）。

## 9.4 重演与"最近作业"（2026-09-15 晚）

**`POST /api/dispatch/runs/{dispatch_id}/replay`**，请求 `{ speed?, dispatch_id? }`（`speed` 默认 60，`dispatch_id` 可选＝新作业号）。

用**存下来的同一批输入**（`context.input` 的 orders/inventory/vehicles）重新规划并**立即发车**，返回新作业的完整视图
外加 `replayed_from`（源作业号）。**旧作业保留为历史**——这不是时间旅行，而是"把这批订单再跑一遍"。
没有存下来的输入 → 409；作业号未知 → 404。

存在的原因：模拟时间按墙上时间推进，一次演示跑完后面板没有任何在跑的作业，
页面会退回离线演示路线 —— 于是"想再看一遍"没有入口。

**`GET /api/dispatch/runs?limit=5`** → `{ runs: [{ dispatch_id, status, updated_at }] }`，最近更新的在前。
永不为 404（空列表＝还没建过作业）。前端据此在作业结束后提供「重演上一次作业」。

**时钟新增字段 `depart_min`**：`sim_start_min` 是"现在几点"的基准（改倍速会重算它），
`depart_min` 是**车队出发的那一分钟**（行程原点，任何情况下都不动）。
车辆位置与到达判定都从后者推导；把两者混为一谈会让改倍速时所有车瞬移回仓库、且送达不再落账。
旧数据缺该字段时回退到 `sim_start_min`（即旧行为）。

**`tick` 每次最多补 30 秒真实时间**（`tracking.MAX_TICK_SECONDS` / `advance_clock`）。
模拟时间由墙上时间推导，没有这个上限时"没人看也在跑"——一次演示放在那里几十分钟，
回来就已经结束（实测用户遇到的就是这个）。盯着看时一秒一次轮询，上限永不触发；
离开后回来是接着看，而不是直接看到结局。倍速 0 仍然是完全冻结。

## 9.5 里程上限与「终点站」＝开环路线（2026-09-16 新增，B2）

`DispatchPlanIn.constraints`（`POST /api/dispatch/plan` 与 `/api/dispatch/runs` 共用）新增两个**可选**字段。
不传时行为与旧版**完全一致**（闭环回仓、无里程上限），所有既有调用方无需改动。

| 字段 | 类型 | 含义 |
|---|---|---|
| `mileage_limit_m` | `int > 0`（米） | **每辆车每天**允许行驶的总里程。口径按 2026-09-16 拍板：**含**取货前空驶、载货行驶与收尾段（返仓或去终点站）。超出即该车不可行——贪心会因此改开下一辆车，OR-Tools 用 Mileage 维度按车限容 |
| `terminal_facility_ids` | `list[str]`（可选，非空、不重复） | **可作为收车点的节点**，必须是 `network.json` 里存在的 `facility_id`。给定时路线变**开环**：每辆车在最后一个站点后前往**离它最近的**某个终点站，**不计返仓里程**。不给定时仍回仓库 |

**为什么"最近的终点站"而不是"由求解器挑一个"**：终点站的选址在业务上是"车停哪儿方便次日"，
与这条路线本身的最优性关系不大；按"最近"归一化后，模型与排班重建用**同一个函数**计价，
不会出现"模型算 30 km、报表算 38 km"这类两处各算一份的问题。

**响应新增字段**（`/api/dispatch/plan` 的 `zones[]`）：

```jsonc
{
  "terminal_facility_ids": ["D-NORTHPOINT", "D-HOUGANG", "D-BUGIS"],
  "mileage_violations": 0,
  "routes": [{
    "vehicle_id": "VEH-chilled-1",
    "end_node_id": 18,            // 网络节点号；null = 回仓库（闭环）
    "end_facility_id": "D-BUGIS", // 同上，人可读
    "mileage_limit_violation": false
  }]
}
```

**执行侧必须跟着走**：`VehicleProgress.end_node_id` 由计划写入，`tracking.vehicle_track(..., end_node=)`
与 `dispatch_route_view` 的日程/腿都以它收尾。否则会出现"求解器说停在终点站、地图把车拉回仓库"——
这正是 §4.2 纪律里禁止的两处口径分裂（参 `docs/C_配送模块.md` §10 第 13、24 条）。

**前端入口（2026-09-16，B3）**：配送面板「调度约束」组直接编辑这三个值，「应用并重新预览」用当前值重算；预览与建单共用同一个请求体（`stores/dispatch.js` 的 `planBody()`），所以看到的就是提交的。

**本批未覆盖**：分支/应急候选（`/api/dispatch/reshipments*`）仍按"回仓库"口径计算，与开环计划的对照
留到 B6 一并处理。

## 9.6 收工停靠选址 + 不可行理由（2026-09-16 新增，B5 / B7）

### 9.6.1 `POST /api/dispatch/overnight-plan`（B5，只读）

请求体 = `DispatchPlanIn`（次日的固定订单 + 车辆 + `constraints`）**再加一个可选字段**：

| 字段 | 类型 | 含义 |
|---|---|---|
| `today_distance_m` | `{"<vehicle_id>": int}`（米，可选） | 各车**今天已经跑了多少**；与 `constraints.mileage_limit_m` 一起约束今晚的停靠位移 |

响应：

```jsonc
{
  "algorithm": "greedy",
  "totals": {"reposition_m": 10900, "deadhead_m": 14800, "stay_deadhead_m": 22200,
             "saved_m": 7400, "net_two_day_m": -3500},
  "choices": [{
    "vehicle_id": "V-CHILLED-1",
    "from_facility_id": "D-HOUGANG",       // 今天收在哪（调用方给的位置）
    "park_facility_id": "D-BUGIS",         // 今晚停哪
    "reposition_m": 10900,
    "tomorrow_first_facility_id": "H-NTFGH",
    "deadhead_m": 14800, "stay_deadhead_m": 22200, "saved_m": 7400,
    "net_m": -3500,
    "note": ""                             // 见下
  }],
  "assumptions": ["…模拟数据声明…"]
}
```

`note` 取值：`""`（正常）· `mileage_budget_exhausted`（当日里程不够开过去，原地不动）·
`no_terminal_given`（未勾选终点站）· `unused_tomorrow`（次日无任务，原地不动）· `kept_position`。

**口径（必须如实转述）**：停靠位移计入**当日**里程；`saved_m` 是**次日首段**少跑的里程；
`net_two_day_m = saved_m − reposition_m`，**通常为负**——按三角不等式，挪车省下的空驶不会超过挪车本身。
这项决策买到的是**次日更短的首段与更早出发**，不是两日总里程更省。
**仍未做的**：次日**从停靠点排线**需要每车起点支持（B4）；当前排线仍从主仓起算。

### 9.6.2 `/api/dispatch/plan` 的未服务理由（B7）

每个温区新增 `unserved` 数组（与 `unserved_customer_ids` 并存）：

```jsonc
"unserved": [{
  "node_id": 2,
  "facility_id": "H-SGH",
  "order_ids": ["DO-DAILY-H-SGH"],
  "reasons": [{"code": "mileage_limit_exceeded",
               "detail": {"needed_distance_m": 28807, "limit_m": 26000}}]
}]
```

`code` 是稳定标识符，**客户端负责本地化**（与判定 code 同一纪律）：

| code | 客户端应说明 | `detail` 字段 |
|---|---|---|
| `mileage_limit_exceeded` | 需要多少 km、上限多少 | `needed_distance_m`、`limit_m` |
| `time_window_infeasible` | 最早几点到、最晚几点、迟多少分钟 | `earliest_arrival_min`、`latest_min`、`late_by_min` |
| `capacity_exceeded` | 需多少单位、车容多少 | `needed_units`、`capacity_units` |
| `closing_window_exceeded` | 收车时间 | `closing_min` |
| `stop_limit_exceeded` | 每车最多几站 | `max_stops_per_vehicle` |
| `no_vehicle_available` | — | — |
| `placeable_in_isolation` | 单独/换个位置放得下，是求解器没排进去 | `fits_after_distance_m` |

**纪律**：这些理由必须由**实际尝试插入**得出（`optimisation/feasibility.py` 用与求解器相同的
`evaluate_route` 判定），**不得**由求解结果反推措辞；数值取"最接近可行"的那次尝试，
以免把"差一点就能送"的订单说成毫无希望。

```jsonc
{ "schema_version": 1, "assumptions": "…",
  "points": [
    {"facility_id": "W-WESTGATE", "kind": "warehouse", "supplies": "all",
     "demo_quantity": {"vaccine_2_8": 600, "insulin_2_8": 400, "frozen_m20": 300, "mrna_ultracold": 200}},
    {"facility_id": "D-NORTHPOINT", "kind": "distribution",
     "supplies": {"vaccine_2_8": 90, "frozen_m20": 60}}
  ] }
```

| 规则 | 违反时 |
|---|---|
| 恰好一个 `kind: "warehouse"`，且 `supplies: "all"` + 覆盖全部目录产品 | 报错 |
| `facility_id` 必须存在于 `network.json`，`role` 与 `kind` 匹配（`depot`↔`warehouse`、`distribution`↔`distribution`） | 报错（第三方仓因此无法被提为主仓） |
| 每个分拨点最多 **2** 类产品（2026-09-16 决定） | 报错 |
| 每个 `product_id` 必须在目录里；数量为非负整数 | 报错 |
| **不在表里 = 不能供货**（医院无需列出） | — |

**可用量解析顺序**：① 台账里存在该 `facility + product` 的记录 → **聚合台账可用量**（真实 0 就是 0）；
② 台账里没有这一对 → 用 `demo_quantity` / `supplies` 的**演示值**，并由调用方在响应 `note` 里声明是模拟值。

## 9.8 订单起点 `origin_facility_id`（2026-09-16 新增，B1b / B4）

`DispatchOrderIn` 新增**可选**字段：

| 字段 | 类型 | 含义 |
|---|---|---|
| `origin_facility_id` | `string \| null` | **这批货从哪个节点取**。不给＝默认主仓（`DISPATCH_ORIGIN`，现为 `W-WESTGATE`），因此既有 payload 行为完全不变 |

**校验链（任一不满足都返回 422，理由带具体的节点与产品）**：

1. 起点必须是 `supply_points.json` 里的**供货点**（医院永远不能当起点）；
2. 该供货点必须**供应这个产品**（`D-BUGIS` 不供疫苗 → 即使它有别的货也拒绝）；
3. 该起点必须**有这批库存**（`insufficient available inventory for vaccine_2_8 (chilled) at D-NORTHPOINT`）；
4. 该起点必须**有一辆该温区的可用车**（`no available vehicle for temperature zone chilled at D-NORTHPOINT`）；
5. 起点不得等于终点（`an order cannot be picked up where it is delivered`）。

**排线语义（B4）**：规划器按 **（`temperature_zone` × `origin_facility_id`）分组**，每组以该货源点为出发仓
独立求解；`/api/dispatch/plan` 的 `zones[]` 因此**每个货源点一组**，每组带 `origin_facility_id`。
里程上限、时间窗、载重、每车最多站点、终点站（开环）等约束**每组独立生效**。

**明确边界**：**同一辆车一天服务多个不同货源点的订单**需要完整取送（PDPTW）模型，本版未实现；
分组模型下跨货源点是"多派一辆车"。车队上限 `max_vehicles` 是**跨组共享**的（先到先得），
超限时返回 `fleet limit leaves no available vehicle for zone … at …`。

## 9.9 报废救援：事件随输入带上「属于哪张订单」（2026-09-16 新增，B6 第一半）

`EventIn` 新增**可选**字段：

| 字段 | 类型 | 含义 |
|---|---|---|
| `order_id` | `string \| null` | 这次温度异常**属于哪张运输订单**。输入本身就是我们自己模拟的，所以这个关联随输入一起来 |

**接上之后拿到的（不再靠猜）**：

| 需要 | 来源 |
|---|---|
| 收货医院 | 该订单的 `destination_facility_id`（**不再需要结案表单那个下拉框**） |
| 补发数量 | 该订单的 `quantity`——**整单全损**，所以"补多少"就是"这单载了多少"（不再用目的地节点的演示 demand 30） |
| 在哪辆车上 | 运行状态 `assignments[order_id] → vehicle_id` |
| 涉及哪些批次 | 运行状态 `reservations[order_id] → ((lot_id, take), …)` |
| 产品 | 该订单的 `product_id`（与事件的 `product_id` 必须一致，否则 422） |

**校验与降级**：
- `order_id` 指向的订单**必须在当前进行中的作业里**，否则 422（不做静默降级——这个关联的意义就在于它是真的）；
- 不给 `order_id` → 走旧行为（`event.destination_facility_id` + 节点 demand），响应里 `order_source` 标注来源；
- 响应新增 `order_source ∈ {linked_order, event_fallback}`，便于审计这次救援的字段到底是哪儿来的；
- 案级错误优先：`reshipment_required=false` 的案子先报"不需要补发"，不会被"没有进行中的作业"掩盖。

**仍未做（B6 余下部分，按顺序）**：
1. **取货点改为"最近的、有货的货源点"**（`dynamic_problem` 仍在 4 处假定 `DISPATCH_ORIGIN`；供货表已就绪但没有用于救援候选）；
2. 出事车辆**剩余站序重排**（现只支持"+1 站"）；
3. **货还在车上**（`stage=transit`）那一支：车上报废货的处置与剩余订单交接——需要动"车辆载了什么"的建模，改动最大。

### 9.9.1 救援候选新增两个字段（2026-09-16，B6 余下两项）

`/api/dispatch/reshipments/preview` 的每个候选新增：

| 字段 | 类型 | 含义 |
|---|---|---|
| `pickup_facility_id` | `string \| null` | 这一方案从**哪个货源点**取货。`null` = 货已在车上（`add_stop_in_transit`）或车就停在货源点上 |
| `remaining_order_ids_after` | `string[]` | 采用该方案后，该车**剩余订单的服务顺序** |
| `resequenced` | `bool` | 该顺序是否与原队列不同（有界 2-opt 的结果） |

**取货点怎么选**：候选构造时先求"供货表说它供这个产品 **且** 请求台账里确有足够库存"的货源点集合，
再按 `从车当前位置到该点 + 从该点到医院` 两段之和最小来选。**供货表给许可，台账给事实**——
表里的演示数量不算库存，所以一个只在表里"有货"的点不会被选为取货点。

**接受时的落库**：批次在**该候选选定的货源点**预留（不再固定主仓）；
若该点不是车辆当前所在，则记入 `VehicleProgress.pickup_facility_ids`，
车辆必须先到那里——这条腿会同时出现在 `GET /api/dispatch/active` 的
`route_view.routes[].stops[]`（首站，`kind: "pickup"`，`order_id: null`）与时钟的到达判定里。
**接受后的剩余队列就是候选给出的 `remaining_order_ids_after`**，保证跑的计划＝比较过的计划。

### 9.9.2 「货还在车上」这一支（2026-09-16，B6 最后一块）

`/api/dispatch/reshipments/preview` 的响应新增：

| 字段 | 类型 | 含义 |
|---|---|---|
| `quarantine_order_id` | `string \| null` | **还在车上**的那张报废单；`null` = 货已在收货点（我们此前的演示主线） |
| `quarantine_vehicle_id` | `string \| null` | 载着它的车 |

每个候选新增 `quarantine_order_ids`：采用该方案时要**在取货点交出**的报废单列表。
有 `pickup_facility_id` 的候选会带上它（交回与领取在同一站完成）；
`add_stop_in_transit` 不设停靠点、因此为空——这条同时写进响应的 `limitations`。

`POST /api/dispatch/reshipments` 的响应新增 `scrapped_order_ids`：本次操作**核销**了哪些订单。
被核销的订单在状态里为 `status = "scrapped"`（既非待送、也非已送达），
其 `remaining_order_ids` 中不再包含它——**时钟因此不会把它记成送达**。

**只对在车上的货核销**：已送达的订单保持 `delivered`（事实是它确实交付过）。
`GET /api/dispatch/active` 的 `metrics` 新增 `orders_scrapped`，否则报废单在界面上无处可见。

## 9.10 取送排线（PDPTW）开关：`routing_model`（2026-09-16，规划侧）

`DispatchConstraintsIn` 新增：

| 字段 | 取值 | 含义 |
|---|---|---|
| `routing_model` | `"grouped"`（默认）/ `"pickup_delivery"` | 前者：每个（温区 × 货源点）一支车队，**一辆车只服务同一货源点的订单**。后者：每个温区一支车队，**一辆车可以沿途从多个货源点取货**（取送问题，PDPTW） |

**取送模式的行为**：
- 订单仍逐单校验"起点是供货点且供应这个产品"；但**车辆校验放宽**为"本温区有可用车"——
  车可以从任意位置出发再开去各货源点（`vehicles_anywhere`）。
- `/api/dispatch/plan` 的 `zones[].origin_facility_id` 为 **`null`**：每张订单自带起点，不存在"本组起点"。
- 路线的 `stops[]` 会同时出现 `kind="pickup"` 与 `kind="delivery"`，**送达点顺序**即 `customer_ids`/`order_ids`；
  完整行驶序列见 `stops` 的顺序。
- 里程上限、终点站（开环）、每车最多站点**照常生效**（与 B2 组合，有测试）。
- `zones[].routing_model` 回显本组用的模型；`stops[].kind` 对**两种站都给**
  （`"pickup"` / `"delivery"`），前端据此区分"这一站是装货还是交货"。
- **`algorithm` 可取 `greedy` 或 `ortools`**（第 4 步起贪心也有成对插入）。
  计划名回到 `algorithm` 字段里：`greedy-pair-insertion-pickup-delivery` /
  `ortools-pickup-delivery`。`algorithm="ga"` 会返回 422：遗传算法只覆盖**单起点、
  货在起点上车**的模型，无法表达成对取送（`ga_solver.solve_ga` 对取送实例同样直接拒绝）。

**执行侧（第 4 步起可用）**：取送计划**可以建单执行**。
- `POST /api/dispatch/runs` 建单后，`state.vehicles[<id>].drive_plan` 给出**完整行驶序列**：
  `[{"kind": "pickup"|"delivery", "order_id": ..., "facility_id": ...}, ...]`（含已完成的站，永不裁剪）。
  它随 run 一起持久化；老状态没有这个字段时按"空 ⇒ 用订单队列"读回，**老 run 仍可 replay**。
- 时钟按**计划下标**判到期：`track.reached_stops > 下标` ⇒ 该站已过。
  对分组路线这与旧口径 `reached - 取货数 > 已送达数` **完全等价**；对取送路线，
  它保证"**取货点没开到就不算送到**"。
- 站点落在**仓库节点**上时也照常计数（修掉了 `vehicle_track` 用"终点不是仓库"判站的旧口径：
  取货点常常就是主仓）。
- `accept_plan` 扣库存改为按**订单自己的起点**（`origin_facility_id or "W-WESTGATE"`），
  与 `validate_dispatch_inputs` 的逐单校验同源；多货源计划因此不再被"主仓没货"卡住。

**同一步声明的限制：取送作业不接报废救援**。`/emergency-preview` 对取送 run 返回 **422**、
`/emergency-accept` 返回 **409**，`detail` 说明原因与出路
（`routing_model='grouped'` 重排当天批次）。原因：救援按**订单队列**插入并重排队尾，
取送 run 按显式**站点序列**行驶，只改队列会让新订单挂在一辆不会开到它那里的车上。
两个入口共用同一处判断（`dynamic_problem._refuse_paired_run`），**不会出现"预览能选、接受才报错"**。
