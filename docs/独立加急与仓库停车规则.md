# 独立加急与仓库停车规则（演示版）

## 当前业务边界

系统演示的是配送路径、时间要求、车辆和突发任务，不是量货或仓库库存管理系统。
独立加急只填写药品、提货仓库、收货医院、最晚送达和可选最早送达；不录入具体货量或仓库余额。
旧数量／批次字段保留给模型兼容、算法实验和历史回归，不代表拿到了真实业务库存。

新的加急任务用一个**无实际载货重量的任务标记**接入共同执行状态，不把标记解释为“一箱货”。
预览在内存准备模拟供货能力，仓库模拟余额为零不会拒绝这张加急单；既有批次余额不被恢复或改写。
是否可供某品类仍按供货表判断；不因为加急自动添加新车辆或伪造温区能力。
后续温度异常关联此任务时也注明标记性质，替代任务沿用这一性质。

## 操作流程

1. 在 API 模式生成、确认当天作业；加急不能另起一个无关作业。
2. 打开配送面板的“独立加急配送”，填写药品、合法提货仓库、医院和当天时间要求。
3. 点击“比较加急配送方案”，查看发车前加入／在途同源备用品加站／回仓提货／备用车等候选。
4. 候选显示新增里程、预计送达、对已有订单的影响、最后停靠仓库及不可行原因；选中后地图显示前后路线。
5. 明确采用，任务写入原作业，地图、订单和执行队列同步更新；不创建温度异常记录。

沿用原有约束：时间窗、温区、可用车辆／车队上限、每车站点、含已行驶及收尾路段的当日里程、营业窗和终点限制。
数量抽象不意味着路径或车辆无限可用；不允许为加急把原来准时的订单变成迟到。
用户指定的提货仓库不会被偷偷换成另一仓库；同源备用品才可使用直接在途加站候选。
PDPTW 在途插入仍明确拒绝，需使用 grouped 模型；当日已结束或截止时间已过也不能偷偷挪到次日。

## 五个合法停车仓库

| 节点 | 模拟角色 | 可作最后停靠 | 可作提货点 |
|---|---|---|---|
| W-WESTGATE | 主仓 | 是 | 全目录品类 |
| W-KN-PIONEER | 第三方／比较仓 | 是 | 当前供货表未启用，仅停靠 |
| D-NORTHPOINT | 北部分仓 | 是 | 供货表指定品类 |
| D-HOUGANG | 东北部分仓 | 是 | 供货表指定品类 |
| D-BUGIS | 南部分仓 | 是 | 供货表指定品类 |

用户在前端多选允许停靠的仓库；医院只是收货点，不能作为当天最后停靠点。
前端选择器只列这五个仓库；后端静态规划、取送模型、应急共同约束和跨天停车都会验证。
没有显式选择时沿用回起点／货源仓库的闭合路线；医院位置不能作为“保持原位”的合法停车。
仓库不是供货点的同义词：第三方比较仓可以停车，不会因停车资格而自动获得供药资格。

闲置车也必须符合选择的停车集合；如果人在医院或未允许的仓库，需真实计算移到允许仓库的路程和时间。
预算或营业窗不足时明确给出不可行结果，不把“留在医院”伪装成停车成功。
旧规划若曾选过医院终点，需重排成仓库终点；不会把历史坐标悄悄改写成仓库位置。

## 默认跨天演示不维护量货余额

前端跨天预览／确认使用 `demo_replenish=true`，按演示假设自动补充次日所需的兼容供货标记，
不再要求用户逐仓填写数量。旧已消耗批次不恢复，新增标记明确标注 DEMO；临时加急不复制到次日固定批次。
研究／历史 API 可继续用默认 `demo_replenish=false` 做数量型库存实验；那不是前端默认业务流程。

## API 与并发

- `GET /api/dispatch/urgent-options`：品类、供货能力、医院收货窗和五个仓库；不返回仓库余额。
- `POST /api/dispatch/runs/{id}/urgent-preview`：`request_id, product_id, origin_facility_id, destination_facility_id, latest_min`，可选最早分钟和排名策略。只读，返回 `state_version` 与候选。
- `POST /api/dispatch/runs/{id}/urgent-accept`：上述字段加 `candidate_kind, vehicle_id, command_id, expected_version`。接纳前重新校验候选。

新的请求模型拒绝 `quantity`／`inventory` 等额外字段。`request_id` 在同一作业内标识同一草稿，
同请求和同选择重试不会重复插入；复用 ID 改内容／改选择会被拒绝。状态、请求审计和执行日程原子保存。
旧 `/emergency-preview`／`emergency-accept` 保留作数值模型兼容，新前端入口不要求其量货输入。
