## 2. 这几天讨论后加出来的设计需求（原计划里没有，需要新写进契约/代码）

这几条本质上是同一套机制的不同侧面，建议合并成一次设计和实现，不要分开做：

- **求解器支持"客户子集"入参**：现在 `solve_greedy(instance)` / `solve_ortools(instance, ...)` 只能吃"整个算例"，没有"这一趟只服务哪几家"的参数。这一条同时解决两个需求——B 提的"演示时前端勾选服务哪几家医院"、以及下面"补发单动态路由"都需要它，应该一次做好，不要各做一次。
- **补发单的"插单 vs 专车"判断逻辑**：一张新的补发单进来，先判断能不能插进当前还在跑的某辆车的剩余路线（不超医院时间窗、不超冷链能承受的最大脱离时长）；插不进去（比如车都跑完回仓了）就直接从仓库单独派一辆车点对点直送这个目的地，不绕道其它医院。现在的做法是"不管什么单都把 10 家医院整网重算一遍"，这条要把它替换掉。
- **车辆中途故障的局部重调度**：车辆冷藏机组故障、GPS/温度异常时，只重新安排"这辆车剩下还没送的站点"，不牵动其它车辆和已经服务完的站点——现在因为是整网重算，天然做不到局部处理。
- **药品温层作为硬约束**：现有产品已经有 2-8°C、冷冻 -15~-25°C、超低温 -60~-80°C 三种温区（`src/rule_engine/rules_config.json`），不同温层不能随意合装同一辆车/同一趟专车，这个约束现在路线求解器完全没建模，补发单被当成一个抽象的"需求单位数"塞进任意车辆。
- **`priority` 字段真正参与决策**：目前 `disposition`（scrap/quarantine）被原样存进 `priority`，但求解器不读它。需要定义清楚：报废+需要补发 → 一定要走（紧急程度取决于目的地库存还能撑多久）；隔离 → 通常先扣着，不一定要立刻派车。这条需要和 A 对一下语义（见第 3 节）。
- **"剩余保质期 vs 剩余路程"的动态时间窗**：由 M2/M3（偏移检测/规则引擎）现有的时长+MKT 判断逻辑，从"只在事后判一次"扩展成"能持续估算出这批货大概还有多久会被判定报废"，把这个报废时间点当成一个会不断收紧的截止时间，叠加在 VRPTW 的时间窗上：按当前路线能不能赶在报废前送到——能就照送，不能就改道送去别的也需要这个药的医院，哪儿都送不到就提前判报废、车直接返仓不用再跑这一趟。真实世界有对应先例（DeltaTrak 的 Freshness Index 曾经真实发生过"预测剩余保质期不够，把货物改道送去更近的分销中心"这样的操作），不是凭空设计。
- **医院端最小数据通路（不是完整门户）**：上一条"改道送去别的医院"需要知道"哪些医院也需要这个药、现在能不能收货"，这需要医院这边至少有一个能表达"缺货/能否接收"的数据接口，不需要做成完整的申请审批门户，先有个最小的数据源即可。

## 3. 需要跟别的角色对齐，C 不能单方面定的事

- **`priority` 语义要不要扩展**：现在契约（`docs/接口契约.md` §1）写的是只有 `scrap`/`quarantine` 两种取值，跟 A 确认要不要加紧急度分级（比如"目的地库存还能撑几天"这种信息从哪来、谁计算）。
- **`EventIn` 要不要接受持续的温度流，而不只是一次性偏移事件**：这个改动如果要做，会动到 A 负责的规则引擎输入接口，需要 A 先点头。
- **医院端数据谁定义、谁维护**：目前七个模块（M1-M7）里没有这一块，如果要做，需要团队一起决定要不要新增范围，不是 C 一个人能拍板的。
- **`/api/route` 的返回结构可能要跟着改**：现在是"整网重算"的结果，如果换成"子集求解"，`RouteOut` 的字段含义会变化（比如"这次路线只服务了这一个目的地"和"这次路线服务了全部 10 家"，前端展示逻辑不一样），`frontend-vue/src/components/ReroutePanel.vue` 已经在解析现在这版返回结构，改之前要和 D 对一遍，别默默改字段语义。

## 4. 建议的落地顺序（按依赖关系，不按日期）

1. 先在 `src/optimisation/` 内部给现有求解器加"客户子集"入参（新增可选参数，不改变默认行为），配单测——这一步完全在 C 自己的文件里，不需要动别人的东西。
2. 基于子集能力，实现"插单 vs 专车"的判断函数——同样是 C 自己文件里的新函数。
3. 温层约束建模——DAILY_PLAN 原计划就有这条，优先级不变，现在细化了。
4. 让 `priority` 真正参与判断——这步要先跟 A 对齐语义（第 3 节第一条），对齐完再动代码。
5. "剩余保质期"动态时间窗——这步需要 A 那边的 M2/M3 提供一个新的输出（"预计报废时间点"），需要先跟 A 对接口，再由 C 消费这个输出。
6. 把以上几步接进 `/api/route`，和 D 对一遍返回结构变化，联调。
7. 医院端最小数据通路——范围最大、影响面最广的一项，建议放最后，而且需要团队一起决定要不要做，不是 C 自己先做了再说。
8. GA 求解器（deap）——跟以上各项相互独立，可以随时并行推进，不依赖它们。
9. 鲁棒性测试、运行说明文档、报告章节、演示脚本——收尾工作，跟以上各项完成度同步跟进。
