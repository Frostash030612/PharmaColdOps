# M2：模拟温度序列 → 偏移窗口 → 实际 MKT → 异常登记

**2026-10-03 更新**：计算契约仍按下文；无法自动处置的窗口现在可以登记为待人工审核，也可登记整段观察（包含全部缺测），
不编造事件数值。审核结论单独保存并驱动后续模拟配送，详见 [人工审核与有效处置](人工审核与有效处置.md)。
下文“阻断登记”指不能进入自动处置／执行，不再表示完全没有人工审核登记入口。

本轮实现提案 M2 的演示链路，不接真实传感器，不预测未来 30／60 分钟，不改 M3 的既有阈值或 M4 特征。
原滑块和预设场景仍是手填演示输入，反向生成的示意曲线不再冒充原始序列。

## 页面使用

1. 启动现有 FastAPI 与 Vue，页面 URL 带 `?api=http://127.0.0.1:8000`。
2. 顶部 `+` → 选择关联订单／产品、发生地点和收货医院 → **M2 · 序列计算**。
3. 选正常／高温／低温／多窗口／缺测场景、种子、观察时长和区间长度，点“生成并分析”。
4. 可展开 JSON 编辑器修改模拟区间，再点“分析编辑后的序列”。修改后旧分析与选中窗口失效，登记禁用。
5. 选用可登记的窗口。温度／时长／MKT 自动填入且不可手改；发生地点、包装、阶段、备注仍可填。
6. 登记后详情显示原始区间图、覆盖率、各窗口、累计暴露与首次分析快照；历史重开不重新计算。

正常序列不生成假异常。缺测不能登记自动处置。离线规则沙箱不调用 M2。
默认手填模式完全兼容旧客户端，但明示 MKT 是演示输入。返回手填是明确用户动作，不是分析失败后的自动降级。
M4 仍需独立、完整的人工模拟／留出样本上下文，不从温度序列捏造湿度、月度设备信息或运输天数。

## 输入与算法契约

实现：`src/temperature_monitoring.py`。以从 0 分钟起的显式区间表示时间序列：

```json
{
  "source": "manual_simulated",
  "observation_end_min": 60,
  "activation_energy_kj_mol": 83.144,
  "intervals": [
    {"start_min": 0, "end_min": 20, "temp_c": 5},
    {"start_min": 20, "end_min": 30.5, "temp_c": 12},
    {"start_min": 30.5, "end_min": 60, "temp_c": 5}
  ]
}
```

每项表示 `[start_min,end_min)` 内恒温，不暗自假设采样间隔，不插值、不外推。
必须正时长、按时间排序、不重叠、落在观察时域内；null 或未覆盖时间是缺测。
拒绝 NaN／Inf、绝对零度及以下、超过演示温度上界 200°C、超长时域和超大数组。
演示分析最多 7 天／10,000 个区间；模拟器支持 30–1,440 分钟和 1–60 分钟区间，至少六段。

MKT 不是算术平均。对已知区间，`w_i = Δt_i / ΣΔt`，`T_i = temp_c + 273.15`：

```text
A = Ea × 1000 / R
MKT_C = -A / ln(Σ w_i × exp(-A/T_i)) - 273.15
R = 8.31446261815324 J/(mol·K)
```

使用 log-sum-exp 避免极低温下指数下溢。Ea 默认 83.144 kJ/mol，可编辑 20–200 范围，
**只是公开定义中的常用默认参数在本演示中的假设，不是四种药品的实测参数**。
定义与单位参考 [USP 〈1079.2〉公开资料](https://www.usp.org/sites/default/files/usp/document/supply-chain/apec-toolkit/USP%20GC1079.2.pdf)，
该公开文本自身注明不是现行官方标准。时间权重是本实现对不等长恒温区间的显式积分约定，不声称临床／合规有效性。
MKT 不能证明冻结安全，尤其不能用极低 MKT 给生物制品放行。

偏移按产品标签范围检测：`temp > max` 为 hot，`temp < min` 为 cold，等于边界不算偏移。
连续同方向区间合并；正常段、缺测、时间间隙和冷热方向变化均切断窗口。
每窗口保留起止、精确时长、最低／最高温、窗口 MKT；整个时域另给已知区间 MKT、覆盖率及冷热累计分钟。
M3 的事件温度取热窗口最高／冷窗口最低；整数时长向上取整，MKT 不先舍入。
**M3 针对选中连续窗口评估，不代表整批放行，也不自动合并累计多次暴露。**

## API 与归档

- `POST /api/m2/simulate`：产品、场景、seed、观察终点、区间长度 → 原始模拟序列、生成配置与分析。
- `POST /api/m2/analyse`：产品 + `series` → 分析，均只读，不登记／发车／改库存。
- `POST /api/decide`／`POST /api/case_close`：可选 `temperature_context = {series, window_id, method}`。
  事件三个数值必须与所选窗口相符，服务端重新计算并校验，不信任提交方填写的 MKT／持续时间。
- 首次登记保存 `temperature_context` 和 `temperature_assessment`：原序列、方法版本、参数、源 SHA-256、储存边界、
  覆盖、窗口、选中窗口与局限。它们进入 SQL 原始记录／兼容 JSONL；图谱仍接收原有判定事件和证据链，
  完整温度序列不新建图谱节点，不伪装法规证据。
- 幂等指纹包含完整温度上下文；同身份同请求优先读取原记录，算法／规则变化不重算。
  同身份改序列、参数或选中窗口返回 409。未携带上下文的旧指纹保持不变。
- 源 hash 标识输入，不是传感器签名；`source=simulated` 也不是来源真实性认证。

## 明确的阻断与剩余边界

缺测仍返回“仅已知区间 MKT”，不可宣称完整监测或整段安全，自动登记一律阻断。
低温窗口均被识别，但现有 M3 仅有冻敏产品 ≤0°C 的冻结规则；其余低温窗口阻断登记、提示人工审核，
不借 M2 偷改已经独立标注的处置规则。手填模式原规则语义未改，也不能用它绕过审核来声称 M2 已判安全。
未来若扩充低温规则，应单独补证据与人工标注，再扩展该入口。
真实传感器接入、采样误差／插值模型、药品专属活化能、累计多窗口质量裁决与未来预警不在本轮范围内。
