## 1. 目标逐条：现状、证据、缺口

### A. 主线与支线

**G1 每日固定配送＝主线，异常＝支线。** ✔
会议原意：先有"每天固定送什么"这条主线，系统检测的是**主线运输途中出的问题**（温度异常等）；
"每天固定任务"之外还会有医院突然说要东西。
现状：主线由 `src/optimisation/daily_orders.py` 生成一批医院订单 → 规划器排线 →「确认」建作业 →「发车」；
支线（结案的温度异常）不再自己开作业，而是**插进当天这条作业**。
证据：`src/api/service.py` 的 `route_reshipment()` / `reshipment_branch_plan()`、`active_plan_run()`；
测试 `tests/test_reshipment_bridge.py`、`tests/test_branch_events.py`。
缺口：会议设想的"实时监测"目前是**前端轮询驱动**的演示态，不是常驻服务（见 G5）。

**G2a 固定出一批任务，点确认就是当天任务。** ✔
现状：面板「🎲 生成今日批次（按日期）」+「⚡ 一键生成并建作业」（**一步含发车**）；
`?seed=today` 按当天日期派生，同一天内可复现、跨天自动变——这是"像公司每日配送数据"的离线等价物。
证据：`GET /api/dispatch/daily-orders`、`src/optimisation/daily_orders.py`、`frontend-vue/src/stores/dispatch.js`。

**G2b 每天自动触发一批（服务端定时）。** ✘ **本阶段不做**（评审决定，2026-09-16）
**没有服务端定时任务**（没有"每天 08:00 自动出批次"）；批次由人点或由外部调用产生。
离线演示里用 `seed=today` 代替"今天是哪一天"这一层语义。
**注意：这是"明确决定本阶段不做"，不是"忘了做"。** 将来要做时的落点：服务端定时器 + 一批订单的持久化。

**G3 出问题时：改现有车的路线，还是另派一辆。** ✔
现状：四类候选一次算清并可比——
`add_stop_in_transit`（用车上余货顺路加一站，不回仓库）／`load_before_departure`（发车前带上）／
`return_to_depot`（折返仓库取货再送）／`spare_vehicle`（另派一辆）。
每类都给里程、ETA、**谁被拖迟**（区分"因此变迟"与"本来就迟"），并可在两种排序口径间切换。
证据：`src/optimisation/dynamic_problem.py`、`POST /api/dispatch/reshipments/preview`、
`frontend-vue/src/components/ReroutePanel.vue`、测试 `tests/test_dynamic_problem.py`、`tests/test_branch_events.py`。
说明：会议里"改道"与"派车"这两种做法，代码里都比当时设想的更细了一层。

**G4 规程之外的临时需求（加急）也要能处理。** ✘ 待做（评审改判：从 ◐ 改为 ✘）
现状：`DeliveryOrder` + 应急插单的**机制**都在（上面 G3 的四类候选就是为它准备的），
但**没有任何入口能录入一张加急单**——今天唯一能产生订单的路径是"结案 → `build_delivery_order()`"，
它绑定在温度异常的处置结果上（`reshipment_required` 为真才有单）。
**按"用户今天能不能用"判定：不能 ⇒ 未实现。**
要做的是：一个**加急单录入入口**（选医院、要多少、几点前到），复用同一套候选比较。

**G10 不能只是"单次订单"，要能"每天送"。** ◐ **本阶段暂缓处理**（评审决定，2026-09-16）
现状：主线解决了"一批多站"（每辆车串多个医院），不再是一单派一车。
未定之处：订单**仍是模拟生成**的——但"没有真实订单源"本身是课题前提（离线演示）。
**这条本阶段不处理，之后再定夺**：要么接受"模拟订单"为既定前提并判 ✔，要么补一条真实/半真实数据源。
另外 `docs/C_配送模块.md` §5 B6 记着库存模型过简（每张补发单凭空建一个刚好够用的批次），那属于另一个问题。

### B. 时钟、位置与实时性

**G5 内置时钟。** ✔
现状：模拟时钟（起始分钟 = 首单收货窗）+ 倍速（真实/60×/300×）+ **真暂停（0 倍速，时间真的冻结）** +
「⏮ 重演」（用存下来的同一批订单重跑）；单次 tick 最多补 30 秒真实时间，标签页切到后台自动暂停。
证据：`src/optimisation/tracking.py`（`make_clock`/`advance_clock`/`watched_now`/`schedule_origin`）、
`POST /api/dispatch/runs/{id}/speed|replay`、`tests/test_tracking.py`。

**G6 紧急处置三种做法。** ✘ 待做（评审改判：从 ◐ 改为 ✘，因为没有完整方案）
会议列了三种：**派车**、**让别的车绕道**、**两车汇合把货转过去**。
现状：派车 ✔；绕道 ✔（折返仓库；用车上余货顺路加一站）；
**两辆车汇合 ✘**：模型里车辆之间没有任何关系，也没有"在两车之间转移货物"的库存操作。
**判定理由**：三种只做了两种、缺的那一种正是"紧急"里最需要的一环，所以不按"部分完成"计，整条记为未完成。

**G7 地图上能看到车在跑。** ✔
现状：车标沿**真实道路**移动（按所在路段的多段线插值）、已走过＝灰虚线带 ✓、剩余＝车辆色带站序编号、
图例、选中车辆时其余变淡、可跟随车辆、可「⛶ 展开地图」进大图视图（含时钟/倍速/暂停/改道对比线）。
证据：`frontend-vue/src/components/LeafletMap.vue`、`TransportView.vue`、`src/api/service.py` 的 `dispatch_route_view()`。

**G8 算两车何时交汇、交换物资。** ✘
完全没有。要做得先补两件事：① 车辆位置要有"在两站之间的时刻"（现在有 `track` 的 leg + fraction，够算）；
② 需要一个"两车交汇 = 位置相遇且时间窗重叠"的判定与随之而来的库存转移操作。

### C. 车队与路径约束

**G12 车队上限、一车多点、别把司机当机器。** ✔（2026-09-16）
会议要求的两条限制都已落地：
1. **车辆总数上限**——`DispatchPlanIn.constraints.max_vehicles` 限制进入求解器的车辆；建立作业时只持久化上限内车队，
   后续 `spare_vehicle` 也无法重新使用被排除车辆。
2. **每车最多跑几个点/几个医院**——`max_stops_per_vehicle` 同时进入贪心插入检查与 OR-Tools `Stops` 容量维度。
每日演示默认 **最多 3 辆、每车最多 4 站**，前端排线预览会明确显示；API 可传其他正整数。
（会议里"别把司机当机器"（疲劳）与油耗、拥堵路段，按当时的共识属于"初级阶段先简化"，不在本条判定里。）

**G13 / G17 回起点还是中途中转；哪几家可作为终点站。** G17 ✔ / G13 ◐（2026-09-16）
现状：**已可停在指定节点不回仓**——`constraints.terminal_facility_ids` 给出允许收车的节点集合，
规划器让每辆车收在离末站最近的那个（实测 4 家医院：闭环 38.23 km → 开环 27.99 km）。
**仍未建模**："把某个节点当作中途换装/中转点"，以及"次日从收车点出发"的跨天衔接（属停靠选址 B5）。

**G15 每车里程上限。** ✔（2026-09-16）
现状：`constraints.mileage_limit_m`（米，每车每天，含空驶与收尾段）已是硬约束：贪心在插入校验里拒绝超限插法，
OR-Tools 用 Mileage 维度按车限容。实测上限收到 25 km 时自动从 1 车变 2 车；收到 12 km 时给出"无法服务"而不是超限方案。

**G16 到达时限。** ✔
`DeliveryOrder.earliest_min` / `latest_min` 进入求解模型；超出收货窗的案例会被排到次日（`scheduled_next_day`）。

**G18 加派车 + 多约束一起考虑。** ✔（2026-09-16）
加派车 ✔（规划器自己会开第二辆；应急候选里也有 `spare_vehicle`）；
**"多约束一起考虑"已成立**：车队上限、每车最多站点、温区、时间窗、**每车里程上限**与**终点站集合**
现在同时在同一个模型里生效（`tests/test_route_limits.py` 10 条覆盖）。

**主线的完整链路**
`GET /api/dispatch/daily-orders`（出批次）→ `POST /api/dispatch/plan`（预览排线，不占资源）→
`POST /api/dispatch/runs`（建作业、占库存与车辆）→ `POST …/depart`（发车，时钟启动）→
`POST …/tick`（前端轮询，把到点的送达落账）→ `GET /api/dispatch/active`（面板与地图的唯一数据源）。

**支线的完整链路**
结案（`POST /api/case_close`）→ `POST /api/dispatch/reshipments/preview`（**只读**，列出全部候选与代价）→
操作员选定 → `POST /api/dispatch/reshipments`（带上 `candidate_kind` + `vehicle_id`，**会重新校验**）→
插入当天作业；没有进行中的作业则 **409**（不再自己开作业）。

**地图**：进度分段（已走过/剩余）、站序编号、✓ 徽标、图例、跟随、大图视图、改道前后对比线、

## 4. 新增工作 G20：前端从「以沙箱为主」改为「以地图为主」

> **状态：第一批已实现（2026-09-16）；第二批待做。** 第一批见 §4.5，
> **第二批见 §4.6——推迟但必做**（写在独立的欠账表里，做完一项划一项）。
> 本节是需求与方案，供接手时评审；不含代码改动。

### 4.1 现在的问题（提出者原话的意思 + 我的核对）

- 页面是**三栏以沙箱为中心**：左＝场景预设＋规则配置，中＝决策沙箱，右＝改派＋问答
  （`frontend-vue/src/App.vue` 的 `main` 三栏）。
- **沙箱的输入几乎全部来自场景预设**（`SCENARIOS`，打开页面即载入 R03）：拖滑块、换产品，
  数据始终是"预设场景"，**没有出现实际流程**。
- 地图只是右栏里的一个 **290px 子组件**。
- 结论（提出者的判断）：**以沙箱为主的结构没有实际用途**——它演的是"某个预设场景会怎么判"，
  而不是"今天这批货现在到哪了、出了什么事、该怎么办"。

### 4.2 目标结构（要改成什么样）

1. **地图为主区**：配送路线与车辆是页面主体（复用已经做好的 `TransportView.vue` 大图能力）。
2. **异常事件出现在地图上**：事件在**发生的医院/站点**上有标记（颜色/形状区分状态：待处理、已处理、已结案）。
3. **点异常事件 → 弹出当次沙箱**：把**那一次**的事件参数（产品、温度、时长、MKT、包装、阶段、目的地）
   载入沙箱，让用户看到"当时为什么这么判"。
4. **同时给出对应的解决方案**：即该事件的处置结果与（若需要补发）候选比较，用户可选一条应用。
5. 从"地图 → 事件 → 沙箱 → 方案 → 回地图"形成闭环，而不是"沙箱 → 作业"的单向流。

### 4.3 为什么现在做不到（缺口清单）

| 缺口 | 现状 |
|---|---|
| 壳是沙箱中心的 | `App.vue` 三栏布局；地图在右栏面板内部 |
| 事件不是"一等对象" | 地图上目前只有**当前这一个**支线事件的标记（`dispatch.incidentNodeId` / `branchNodeIds`），没有"全部事件"的图层 |
| 沙箱与作业是单向的 | 沙箱产出喂给作业（`closeAndDispatch`）；**没有"从作业/地图回到某次沙箱"的入口** |
| 事件列表缺位置与状态 | `GET /api/runs` 已经归档案例并带 `event.destination_facility_id`（够定位），但没有"已处理/未处理"的状态字段，也没有"影响哪张订单"（＝B0） |
| 在途异常没有位置 | 车辆位置只有"设施节点"，路上出事只能落在站点（已知简化） |

### 4.4 打算怎么改（清单，供评估工作量）

1. **布局**：`App.vue` 重排为「地图主区 + 侧栏（事件列表/方案/规则）」；
   现有的 `TransportView.vue` 从"弹出的大图"升级为常驻主区；沙箱从"中栏"变成"事件详情抽屉/弹窗"。
2. **事件图层**：新增"事件"数据面（案例 id、位置、状态、处置结果、影响订单），在地图上按状态着色；
   数据源先接 `GET /api/runs`，状态字段需要 A 侧/后端补（跨成员：`ExcursionEvent.facility_id` 与处置状态）。
3. **交互**：点标记 → ① 用已有的 `sandbox.restoreCase(record)` 载入该案例到沙箱；
   ② 展开该案例的方案区（已有 `POST /api/dispatch/reshipments/preview`）；③ 选定后写回作业（已有）。
4. **联动**：地图与方案卡片共用 `frontend-vue/src/stores/dispatch.js` 里已有的
   `branchOverlays / branchNodeIds / incidentNodeId / branchVehicle`，避免两处各算一份。
5. **验收标准（怎么写才算做完）**
   - 打开页面即在**地图**上看到今天的路线、车辆与（若有）异常标记，不必先点沙箱；
   - 点任一异常标记：弹出的是**那一次**的参数与判定，且能一键看到该次的处置方案；
   - 在地图上选定方案后，作业与地图**同步更新**（不必手动刷新）；
   - 关掉沙箱抽屉，页面仍是一个完整的运输视图（沙箱不再是"主体"）。
