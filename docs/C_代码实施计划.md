## 总体实现选择

- 保留现有静态求解器与 Solomon 回归路径。在 `src/optimisation/` 新增业务数据、问题组装、动态调度及统一校验层，不把业务状态塞进原 Solomon 数据类。
- 日常订单直接进入 C；异常经现有 A 处置链转换成受影响任务与补发需求。B 的原实验不变，不假定已有在线 ML 故障接口。
- 后端负责唯一运行状态；前端仅发操作、显示结果。算法比较不扣库存、不发车；确认方案后才预留资源。
- 原 `/api/route` 与静态演示保留兼容入口。新增业务 API 使用独立模型，避免把原单案例响应悄悄改成多订单响应。

## 第 1 批：业务模型与接口样例

**拟新增** `src/optimisation/dispatch_models.py`、`dispatch_validation.py`；`data/optimisation/dispatch/` 放小规模模拟场景。

- 定义订单、库存批次、车辆能力、医院窗口、任务、状态快照、事件与方案。区分配送订单 ID、补发 ID、`run_id`、产品 ID 和设施 ID。
- 明确统一时间原点/时区、数量单位到容量的换算、收货时限指到达还是完成卸货。初版每车单温层，批次库存包括状态和预留量。
- 将处置类别与运输紧急程度分开，不重新解释旧 `priority` 字段。
- 新业务订单缺医院/数量要报错，不继承旧接口“默认第一家医院”的演示行为。
- 和 A/D 定义示例输入输出及职责：C 读取状态并返回方案；D 保存状态及处理命令。

**验收**：同医院多订单可区分；无效设施、数量、时间和温层有明确错误；模拟数据与原标注、训练集分开。

## 第 2 批：按订单排线并连接现有补发链

**拟新增** `problem_builder.py`、`dispatch_planner.py`；**修改** `reshipment.py` 的业务适配，保留旧入口。

- 先检查合格库存、车辆与需求，再构建仅含相关订单的求解问题；设施 ID 与算法内部索引显式映射，不能把子集序号直接用于全量道路矩阵。
- 兼容订单才允许同站合并；结果保留订单映射。按温层分配车队时不重复使用同一辆车。
- 复用贪心/OR-Tools做静态排线；异构容量不能用一个全局容量假装支持，先限制同组车辆容量一致，随后在动态模型显式扩展。
- 适配真实 case_close 结果：定位原订单与批次，生成替换货物需求。缺少必要关联时返回待补信息，不送默认医院。
- 扩展导出器，输出本次计划目标数、实际服务数、未服务订单、道路几何和说明；前端分母不再固定 10。

**A/D 配合修改位置**：`src/api/schemas.py`、`service.py`、`main.py` 增加业务请求和案例关联；保留原规则输入兼容性。Vue 新增订单入口、调整 `ReroutePanel.vue` 与 store，地图复用。

**验收**：三家订单只配送三家；一单异常通过 A 接口生成针对性补发；不重复扣库存或生成补发单；原 API 与 Solomon 仍可用。

## 第 3 批：状态推进和方案执行

**拟新增** `dispatch_state.py`（纯状态转换）；D 侧新增运行存储模块及命令接口。建议小型 SQLite 事务保存，避免多份 JSON 状态分别更新造成错账；由 D 确认并维护。

- 支持确认方案、装货、出发、到站交付和事件录入。确认时检查状态版本并预留库存/车辆；同一命令重试不重复执行。
- 算法切换仅预览。每个方案绑定输入快照版本，过期方案不能覆盖新的运行状态。
- 记录已交付、车载、可用和隔离数量，保持数量守恒。单据关闭与实际交付分开。
- 首版在仓库/医院节点暂停模拟时钟并触发调整；不假装已支持任意道路中点。D 新增车辆列表、推进按钮及历史回放。

**验收**：刷新不丢进度；已送订单不重复；重复命令无副作用；过期方案拒绝执行。

## 第 4 批：在途插单和延误

**拟新增** `dynamic_problem.py`、`dispatch_candidates.py`、`dispatch_evaluator.py`。

- 建模不同车辆起点、当前可用时间、已装载订单、取货先于交付和剩余任务。原 depot-to-depot 求解器不能直接替代这一模型。
- 先实现候选方案：未出发带货、合法在途插单、回仓取货、备用车。统一重新排程和校验，不只比较地图距离。
- 硬约束先过滤；再比较紧急需求覆盖、软迟到、额外距离和对原计划影响。明确每个时间要求是硬约束还是软目标。
- 固定已完成任务，允许必要的其他车辆接替。库存、车载货源与车辆数量均有限。
- OR-Tools 动态适配放在独立模块，扩展车辆起终点与取送约束；贪心候选法作为可解释基线。

**验收**：空车不能凭空补货；回仓和装卸计时；旧订单时限被检查；无可行方案有未服务清单。

## 第 5 批：故障与质量事件重调度

**拟新增** `dispatch_events.py`；扩展候选方案、状态转换与 A/D 适配。

- 区分风险提示、确认故障、质量处置。质量事件经过现有 A 接口；车辆故障来源可为明确标注的模拟设备或人工确认。
- 按车辆/批次/包装关联确定影响范围。原货安置和合格替换货配送是不同任务，关联同一异常。
- 加入指定应急冷藏点、接替车辆、转运服务时间和接收能力。未建立合法转运路径时不生成救援方案。
- B 后续可将已验证事件接入同一适配层，不改原 ML 数据与 gold。没有模型能力时不输出“ML 已确认故障”。
- 可选扩展：任意途中位置救援。需额外保存/加载道路图、匹配位置并计算当前位置到设施的行驶代价；现有 11×11 矩阵不足。此项单独验收，不阻塞节点版。

**验收**：实际 A 处置结果改变 C 可配送任务；隔离货不进入正常交付；救援无资源时明确失败；D 可追溯事件到方案。

## 第 6 批：算法、测试与交付

- 新增 `ga_solver.py`（deap），复用静态模型与统一校验；三算法先完成共同静态问题比较，不将 GA 支持静态宣称为支持全部动态功能。
- 更新实验脚本：同输入、同约束、时间预算与适用种子，记录环境；Solomon 与动态场景分别出表。
- 新增 `tests/test_dispatch_*.py`，每批只运行相关测试；关键验收后再跑一次完整回归和 Vue 构建。
- 动态指标：紧急订单准时完成、未服务量、额外距离、原订单受影响数、计算时间；静态继续使用现有指标。
- 补运行说明、报告优化章节、GeoJSON 导出与五类演示，做一次干净环境复现；统一 OR-Tools 名称。

## 执行边界与开工前需要明确的决定

- 用户确认计划后先做第 1 批；每批单独提交并记录已实现边界，不一次混改所有角色。
- 必需 A 确认：批次处置、补发授权和产品约束来源；若调整规则语义，标注评估是否更新由 A 决定。
- 必需 D 确认：业务状态保存、版本化接口、页面操作与审计工作由谁落地。若用户授权我代改这些文件，应保持兼容并按批次交付。
- 医院需求与库存无真实来源时使用模拟文件；数量、接收窗口、应急点与车辆配置要有说明。
- 暂不实现保质期预测、医院门户或多仓库选址。它们不属于现有数据和模型能直接提供的能力。
