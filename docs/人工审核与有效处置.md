# 规则边界与人工审核闭环

2026-10-03 用户确认：人工审核结论可以作为后续配送的有效依据，但必须保留原始自动建议。
本轮仅实现演示审核，不修改 M3 数值规则、不修改 57 条人工 gold，也不为低温容差编造出处。

## 三层记录

| 层 | 保存内容 | 能否覆盖 |
|---|---|---|
| 原始登记 | event、spec、disposition、rule_no、原始补发标志、M2 原序列／首次计算、M4 首次模型快照、原引用 | 首次记录保持不变 |
| 人工审核 | 审核人、结论、理由／参考说明、时间、请求身份与指纹、版本、补发医院 | 每次追加，不能删除旧审核 |
| 有效处置与执行 | 最新审核推导的有效处置、补发需求、处理进度、实际补发订单／送达 | 单独展示；不反写原始建议 |

旧客户端及历史登记的原始字段仍是原建议，不改名、不偷换语义。
新增 `effective_disposition`、`effective_reshipment_required`、`decision_source`、`review_status` 等字段，后续补发读取有效字段。
历史已结案的旧隔离案例不会被新机制重新打开。原图谱继续描述原登记与原规则引用，不自动给人工结论补法规依据。
QA 会提示解释范围；人工理由保存在审核记录和报告中，不冒称法规已验证了该理由。

## 哪些需要审核

- 原始事件低于储存下限，但未被现行冻敏 ≤0°C 冻结规则覆盖。
- M2 存在缺测／间隙；MKT 只覆盖已知区间。
- M2 存在多个偏移窗口；现行规则只判选中窗口，没有累计多次暴露的质量政策。
- 登记整段观察而非单个窗口；特别是完全缺测／缺测但已知区间正常。
- 操作员主动勾选“申请人工审核”，并填写原因。
- 新登记的自动规则建议为复检，需要明确的结果与后续处置，不以模糊处理备注代替放行。

M2 仍分别标明哪些窗口可自动处置，哪些只能登记待审核。可选择一个窗口，或“登记整段观察，转人工审核”。
整段观察的事件温度／时长／MKT 为 null，不捏造读数，不调用 M3／M4；`automatic_assessment_available=false`。
这类记录中的原 `quarantine` 仅表示**操作扣留**，rule_no=0、无自动处置依据，不是新增的药品质量规则。
正常、完整、无偏移的序列不会自动生成异常；整段观察入口是显式的审核登记。

## 页面流程

1. 顶部 `+` 选择订单、发生地点、产品和医院；输入模拟事件，或使用 M2。
2. 对规则边界／缺测／多窗口自动提示待审核；其他情况可主动申请审核。
3. 登记后，在案例详情的“人工审核与案例审计”填写审核人、结论、理由及参考说明。
4. 原始建议和当前有效处置同时展示。审核后的处置可再次追加修订，直到补发执行或处理完成。
5. 需要补发时，比较和采纳现有配送候选；仍复核车队、温区、时间窗、里程、五仓停车与当天作业约束。
6. 实际补发送达才标为已处理；其他处置需填写处理说明，再填写结案说明。待审核不可提前标为已处理或结案。

| 人工结论 | 后续行为 |
|---|---|
| 继续隔离／扣留 | 继续待审核，禁止补发执行及处理结案；可追加下一次审核 |
| 放行 | 不补发，允许继续原订单交付；处理／结案仍须留说明 |
| 复检 | 中间步骤，继续阻断交付／结案；结果可用后追加明确的放行、报废或继续扣留审核 |
| 报废 | 按有效结论生成补发，需要已知医院；原订单在补发采纳时按既有状态机报废 |

已关联订单不能在审核里换医院。未关联／未填医院时，人工报废可指定一个已知医院，这个选择另行保存，不改原事件。
复检结果仍是用户填写的演示审核，不表示接入实验室或检测了真实药品效价。仅写“复检完成”不能绕过结果审核。

## 交付保护与锁定

待审核、未完成复检、人工已判报废但尚未采纳补发的关联订单，不能被手动交付或自动 tick 交付。
tick 发现有这类未完成订单时暂停**整个演示时钟**，不结算到达；不能用加速按钮绕过。
审核／复检处理／补发采纳完成后，由用户手动恢复。当前只有共享时钟，不声称其他车辆能独立继续运行。
多个案例关联同一订单时，所有仍生效的扣留条件都会参与交付保护。
已送达或已报废的旧事实不撤销，登记不能回溯阻止已经发生的送达。
登记会保存原订单当时状态：货物在登记前已送达的事后复核，可继续追加复检结果，但不撤销送达事实。

补发执行后，或人工处理完成／结案后，不允许改有效处置。人工放行后的原订单实际交付也会锁定。
审核、登记、处理、补发采纳、手动交付、tick 和时钟恢复共用 DB 级互斥保护；补发采纳时重新读取当前有效结论，
旧标签页上的过期候选不能绕过新的扣留或变更结论。派车后若进程在保存锁标志前失败，实际 RO 订单存在也会阻止改审核。

SQLite 使用本机进程锁 + 文件锁（macOS/Linux）；PostgreSQL 使用 session advisory lock。
仅验证了本机 SQLite 与真实 Neo4j，未冒称完成了 PostgreSQL 服务器验收或生产级分布式事务。
这不是全面的物流命令事务锁；既有普通调度命令仍使用原状态机的版本检查。

## API、重试与身份边界

- `POST /api/case_close` 可带 `review_requested=true`、`review_reason`；原因进入登记指纹。
- `temperature_context.window_id=null` 登记整段观察，三个事件数值必须为 null 或不传；不接受 M4 上下文。
- `POST /api/runs/{run_id}/review`：`command_id`、`expected_version`、`disposition`、`reviewer`、`reason`、可选医院。
- 每次审核追加到工作流中的 `review_history`，与操作处理共享版本；并发旧版本返回 409。
- 同一 command_id 同请求幂等，不重复追加；改内容返回 409。重放历史命令返回当前状态，不重新应用旧结论。
- 浏览器保存未确认审核请求，冻结表单并原身份重试。404／422 是明确拒绝，网络／503 等仍保留请求。
  放弃本地请求不会删除后台审核，页面先提醒检查记录。

审核人是**自报演示姓名**，不是认证账号、签名、授权药师身份或权限控制。本轮不建立真实人员认证／审批资质系统。
人工结论驱动的是模拟配送，不能作为真实药品发放、销毁或运输授权。

## gold 与验证

57 条 gold 是既有独立人工参考标签，不是临床金标准或 M4 训练集。本轮不动它，规则仍为 54/57 一致。
S034/S035/S052 保留“历史 gold 待复核”；新审核是运行案例的追加意见，不是偷偷修改评测答案。
自动规则一致性、人工审核的流程正确性、实际药品安全有效性是不同的验证层。

`tests/test_case_review_and_audit.py` 覆盖四结论、完整源、重复／并发、锁定、实际补发、交付阻断、复检、历史兼容及导出。
`scripts/browser_review_acceptance.cjs` 验收完全缺测登记、继续扣留、再审核、响应丢失／刷新恢复、处理结案与下载。
使用独立 SQLite／JSONL／测试图谱；不在本项目运行库写验收案例。
