# 知识图谱可靠性与恢复

## 当前保证

登记权威是关系库的 `case_registrations`，不是 JSONL 或 Neo4j。
`case_graph_outbox` 与新案例**同一事务提交**，保存原始完整判定、原规则引用 ID 和 SOP ID。
旧登记记录首次读库时自动进入待同步队列；不会重新判定、更改原订单关联或覆盖已保存载荷。

Neo4j 单事务提交事件、处置、原因、法规、SOP、发生设施、补发单和目的地。
缺失已声明的 Product／Facility／Regulation／SOP 静态节点时整条回滚，保留 pending，
不创建只有 ID 的空证据节点、不因少写了一条设施边而报告成功。
案例节点标 `simulated=true`，存原 `dispatch_id`／`order_id`，不与 Kaggle 的匿名 Shipment 强行连边。

传递保证是 **at-least-once + 幂等 MERGE**，不是关系库与图谱的分布式 exactly-once：

- pending → 带独立 token 的 processing（60 秒领取租约）→ synced；失败回到 pending，15 秒后重试。
- 领取用 CAS；多个进程不重复领取活跃任务。进程崩溃后租约到期可重领。
- 图谱已成功但关系库确认失败时会重放；同 run_id 不重复生成事件／补发单。
- 过期工作进程不能用旧 token 覆盖新同步结果。
- 登记响应不因图谱失败消失；图谱连接和事务重试有上限，不无限卡住登记。
- `/api/qa` 对仍待同步的已登记案例返回 503，不把它报告成“没有这个案例”。

`GET /api/graph-sync` 只读返回 pending／processing／synced 数量。
**synced 是最后一次写入确认，不是持续连通或图谱从未被清空的证明。**
已登记案例在图谱中丢失，即使队列仍显示 synced，案例级 QA 也返回 503 并提示覆盖审计；
真正没有归档的 run_id 仍返回 `no_case`，不把两种情况混为一谈。

## 实际覆盖审计与选择性修复

```bash
.venv/bin/python scripts/check_case_graph.py --report data/processed/graph-coverage-new.json
.venv/bin/python scripts/check_case_graph.py --repair --report data/processed/graph-repair-new.json
```

第一条**只读**：从关系库原始快照／旧 JSONL 对账实际事件、处置和事实字段、原因、法规、SOP、发生设施、补发单与目的地。
不会创建不存在的 SQL 文件、初始化队列表、迁移表结构或写图谱。已有报告拒绝覆盖；格式错误的归档文件明确失败，
不静默少算案例。关系库原始快照优先于镜像，legacy 引用映射限制仍如前述。

报告区分 `complete / missing / incomplete / conflict`，并列出 queue 状态；
即使链完整，仍有 pending／processing 也不会报告总体通过。空案例集合标 empty，图谱或数据源不可用标 unavailable，
两者返回失败码，不输出冒充通过的 0 条覆盖率。

第二条显式修复：只重排缺失／残缺且静态依赖齐全的案例链，随后再审计；不影响其他 synced 案例或活跃领取租约。
遇到字段矛盾、多处置、重复事件或额外证据边时标 conflict，**不自动删除证据或强行覆盖**，需要操作员核对。
静态证据缺失也不能靠造一个只有 ID 的节点来“修复”。仅待确认的队列仍由自动工作进程／sync CLI 处理。

**本机项目实测（2026-10-01）**：启动原有 `pharmacoldops-neo4j-1`，不清库、不重建。
120 条旧 JSONL 案例在图谱中全部缺失；备份本机 SQLite／JSONL 后，只补写这 120 条缺失链。
再次只读审计为 **120 complete、0 missing／incomplete／conflict、0 待确认**。
旧配送表逐行与备份一致，JSONL SHA-256 前后相同；这些本机运行案例与备份不提交到 GitHub。
项目图谱保留运行状态，故障实验只操作另外创建的临时容器。

## 自动恢复与人工补写

开启 API 的自动补写循环（每 15 秒，单批最多 50）：

```bash
KG_SYNC_ENABLED=1 .venv/bin/python -m uvicorn --app-dir src api.main:app --port 8000
```

默认不开循环，避免没有初始化图谱的纯规则演示反复连接；每次新登记仍尝试一次。
启用上述变量后，Neo4j 恢复会自动重试；待静态依赖补齐或租约到期也会恢复。
不新增公开写接口，防止任何客户端直接触发批量图谱写操作。

也可使用独立工作进程：

```bash
.venv/bin/python scripts/sync_knowledge_graph.py --watch
.venv/bin/python scripts/sync_knowledge_graph.py --force
```

`DATABASE_URL`、`CASE_RUNS_FILE` 和 `NEO4J_*` 必须与目标 API 一致。
`--force` 只跳过失败等待，不抢活跃领取租约。一次运行若还有 pending／processing，返回码 1，
不会输出“全部成功”；用 `--limit 1..1000` 控制单批数量，积压多时重复运行或 watch。

旧 JSONL 原始案例尚未入关系库时，显式迁移到图谱队列：

```bash
.venv/bin/python scripts/sync_knowledge_graph.py --legacy --force
```

按 run_id 去重，关系库原始记录优先，已有载荷不覆盖；坏 JSONL 明确报错，需要人工检查，绝不删除原文件。
旧案例没有冻结引用 ID 时采用当前映射，仅新登记具备原引用快照；不得把旧记录的这种兼容恢复称为历史引用逐字复原。

## 图谱重建后的恢复

**现有 `build_graph` 会清空图谱，包括运行案例。不要在业务库上为验收随意运行。**
已经经过授权重建静态图谱时，关系库案例仍在，但 synced 标记不能代表它们仍在 Neo4j。
重建后显式重排历史案例镜像：

```bash
.venv/bin/python scripts/sync_knowledge_graph.py --legacy --rebuild --force
```

此命令不删除关系库／JSONL、不修改质控结论，只把已同步记录重新标 pending 并重放。
若数据量超过单批上限，继续 watch 或重复执行不带 `--rebuild` 的命令直到队列归零。

## 真实停库／重启验收

```bash
.venv/bin/python scripts/verify_graph_recovery.py
# 若默认 tag 不存在，可用 --image 指定已安装的 Neo4j 5 镜像 ID。
```

脚本自建带独立、固定端口和内存上限的 Neo4j、API、SQLite 与 JSONL，然后**真实停止自己的图谱容器**：
登记仍返回 200，队列 pending，案例 QA 返回 503；重启同一测试容器后，由 `KG_SYNC_ENABLED=1` 工作进程
自动补写，不调用人工 sync。重试原身份仍只一条案例、一条事件、一张补发单，且完整案例 QA 与覆盖审计通过。
Docker 随机分配的端口可能在重启后变化，故脚本选择空闲端口并固定映射，不让测试错误归因于重试逻辑。

证据目录保存 API／Neo4j 日志、容器退出状态、SQLite／JSONL、coverage 和报告；`--output` 要求新目录。
脚本结束只关闭自身 API 和由它成功创建、以不可变 ID 标识的容器及匿名临时卷，不碰项目已有容器。
报告保留，临时图谱可由脚本重新生成；Docker 不可用或恢复失败时返回非零，不冒充已通过。

SQLite 和 Neo4j 本地集成已验收；PostgreSQL 使用同一队列表和事务逻辑，尚无本轮真实 PostgreSQL 服务器验收，
不能把兼容代码支持等同于生产部署已经验证。也未接供应商真实稳定性数据。
